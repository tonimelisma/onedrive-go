## 1. Local trash (internal/localtrash + executor_delete.go + download-overwrite path)

**Directory.** `localtrash.DirForStatePath(statePath)` = `<dir of state DB>/trash/<state DB basename without .db>/` (`internal/localtrash/localtrash.go:135-141`). The state DB is `<dataDir>/state_<canonicalID with ':'→'_'>.db` (`internal/config/drive.go:434-442`). For a personal drive the trash is therefore `~/.local/share/onedrive-go/trash/state_personal_<email>/`. Layout per entry: `<id>/item` + `<id>/entry.json`, `id = <UTC timestamp>-<4 random bytes hex>` (`localtrash.go:12-23, 170-206`). Wired once per engine in `configureEngineExecutor` (`internal/sync/engine.go:282-295`), on the SSD, i.e. a **different filesystem** from `<production sync folder>`.

**How a file enters it on a remote delete.** `DeleteLocalFile` → `removeVerifiedLocalFile` (`executor_delete.go:203-236, 291-313`): `trash.Reserve` writes `entry.json` as `pending` first (`localtrash.go:170-206`), then `syncTree.DetachRegularFile(rel, verify, placement.ItemPath)` (`internal/synctree/detach_unix.go:101-122`):
1. open the file `O_NOFOLLOW` through the parent directory fd, stat-stamp it (size/mtime/ctime), run the verify callback **through that descriptor** = full QuickXorHash of the file against `baseline.LocalHash` (`executor_delete.go:246-287`; no hash in baseline → size+mtime evidence only, else refuse);
2. rename it to a sibling `.onedrive-go.<16 hex>.detach` in the same folder (`setAsideVerified`, `detach_unix.go:250-280`; name constants lines 29-31) and re-check inode and stamp;
3. `moveDetachedOut` tries `renameat(tempName → dest)`; on `EXDEV` (our case) it calls `copyVerified` (`detach_unix.go:361-381, 386-397`): `copyThroughDescriptor` seeks the *same open descriptor* to 0, `os.MkdirAll(dir(dest), 0700)`, `os.CreateTemp(dir(dest), ".copy-*")` (temp lives inside the trash entry dir on the SSD), `io.Copy`, `chmod 0600`, **`tmp.Sync()`**, close, `os.Rename(tmp → dest)` (`detach_unix.go:401-437`; no fsync of the trash directory itself). It then re-stamps the descriptor (`unchangedSince`) and discards the copy if the file was written meanwhile; only then `unlinkat` the set-aside file (`detach_unix.go:372-380`).
4. `commitTrashPlacement` rewrites `entry.json` as `committed` with the size (`executor_delete.go:319-327`, `localtrash.go:221-232`); a failed commit is logged at Warn and leaves a `pending` entry that still lists/restores and is never auto-purged.

**Abort semantics.** If the copy fails (ENOSPC on the SSD, I/O error) `moveDetachedOut` returns the error, `DetachRegularFile` runs `linkBackNoReplace` to put the set-aside file back under its name (`detach_unix.go:114-119, 346-353`), the executor calls `placement.Abandon()` (refuses to remove an entry that holds a file, `localtrash.go:236-244`) and the delete action **fails** (`executor_delete.go:303-309` → `failedOutcome`). The file is **not** removed. Same for the overwrite path: `preserveReplacedDownloadTarget` → `PreserveRegularFile` (hard-link, on `EXDEV`/`EPERM`/`EMLINK` → `copyVerified`, `detach_unix.go:151-180`); an error there fails `ValidateTargetBeforeRename` (`executor_preconditions.go:581-598, 624-642`; hook at `executor_transfer.go:69-83`) so the downloaded `.partial` is never renamed over the old file. Without a trash (`e.trash == nil`, never the case in production) it would unlink.

**No size cap, no free-space check, no configurable location.** `localtrash.go` contains no size or `statfs` logic; the config field table has no trash key (`spec/design/config.md:196-231`); the directory is derived solely from the state DB path (`engine.go:290`). Nothing env-overridable except moving the whole data dir with `XDG_DATA_HOME` (`paths.go:62`).

**Purge policy.** `Retention = 30 * 24h` from `TrashedAt` (`localtrash.go:44`). `Purge` removes only `committed` entries older than that, plus *reservations with no file* older than 1 h (`incompletePlacementGrace`, lines 67, 516-530). **Never purged:** `pending` or `orphan` entries that hold a file. When it runs: `purgeExpiredTrash(true)` in `postSyncHousekeeping` after every one-shot pass that executed something (`engine_housekeeping.go:14-31`, `engine_run_once.go:95-97`) and after watch bootstrap actions (`engine_watch.go:324`); in watch mode the maintenance tick calls `purgeExpiredTrash(false)`, rate-limited to once per hour (`engine_housekeeping.go:35-58`, `engine_watch_maintenance.go:13`). Failures are Debug-logged. `onedrive-go trash list|restore|empty --confirm` operate on the same dir (`internal/cli/trash.go:81-107`); `Restore` copies back across filesystems via a `.onedrive-go-restore-*` temp beside the target (`localtrash.go:394-475`).

**On this host, a remote deletion of the 12.9 GB video:** read 12.9 GB once to verify the hash (single-threaded, through the open fd), rename to `.onedrive-go.<hex>.detach` in its folder, read it **again** while writing 12.9 GB to `~/.local/share/onedrive-go/trash/state_personal_<email>/<id>/.copy-*`, fsync, rename to `item`, unlink the set-aside. At 150–250 MB/s that is roughly 2–3 minutes of reads plus the data-filesystem write, during which the `.detach` name is visible in the folder (excluded from sync by `content_filter.go:139-140`). SSD usage: +12.9 GB for 30 days; nothing reclaims it earlier except `trash empty`. **A re-download of the same file:** the download first writes 12.9 GB to `.onedrive-go.<name>~v<hex>.partial` in the same folder (48 → ~35 GB free), then the pre-rename hook hashes the old file (12.9 GB read), hard-link fails `EXDEV`, copies it to the SSD (second 12.9 GB read + 12.9 GB SSD write), and only then renames the partial over it. All of this is safe (verified inode, nothing destroyed on failure) but costs ~4 full passes over the file.

**Verdict: OK for this deployment (functionally safe); operational cost note — large trash copies cross to the SSD with no cap or knob (see finding 6-5).**

## 2. First sync with no baseline on 129k files

**Order of a live pass** (`engine_current_plan.go:13-36, 183-198`): remote observation and commit → local scan and commit → load planner inputs from SQLite → plan → execute. Startup first loads the (empty) baseline into memory (`engine_startup.go:38`).

**Remote side, first time.** `remoteObserver.fullDelta` with an empty token (`observer_remote.go:189-287`) calls `graph.Client.Delta` on `/drives/{id}/root/delta` with **no `$top`** (`internal/graph/delta.go:35-39`), so the page size is the server default (OneDrive Personal usually ~200 items/page; expect roughly 600–900 pages for 138k items). Every page is appended to one in-memory `window []graph.Item` and classified only after the last page (`observer_remote.go:221-234, 249-250`), with an `inflight` parent map alongside; the `graph.Item` struct carries ~20 strings including `DownloadURL`, ETag, CTag and three hashes (`internal/graph/types.go:47-85`), so the window alone is on the order of 100–200 MB for 138k items. Progress is logged every 30 s (`observer_remote.go:240-247`). The whole batch is written to `remote_state` in **one transaction** (`store_write_observation.go:42-86`, via `engine_mount_root.go:294-306`); the delta cursor is committed only after the plan is built (`engine_run_once.go:159-162, 332-347`). A kill during enumeration repeats it from scratch (no page-level checkpoint).

**Local side: whole tree in memory, not streamed.** `FullScan` (`scanner.go:114-220`) is three sequential phases: (1) `tree.WalkDir` fills `observed map[string]bool`, `currentRows map[string]localStateRow` (every entry), a `jobs []hashJob` slice and `events`; (2) `hashPhase` runs an `errgroup` with `SetLimit(checkWorkers)` (default 4, `scanner.go:77, 268-269`) and appends a `localStateRow` **and** a `changeEvent` per file under one mutex (`scanner.go:329-381`); (3) deletion detection against the baseline. Results are copied again by `sortedLocalStateRows` (`scanner.go:780-793`) and `buildLocalStateRows` (`scanner.go:1469-1473`). With **no baseline every file is a `hashJob` with `isNew=true`** (`scanner.go:679-708`) — every file is hashed, 1.2 TB read in full. The fast path `canReuseBaselineHash` consults the *baseline only* (`local_hash_reuse.go:34-54`), never a previous `local_state`, so an interrupted first scan reuses nothing. There is no batch size: the snapshot is committed in **one `replaceLocalState` transaction** after the scan completes (`engine_current_plan.go:302-315` → `engine.go:334-386` → `store_local_state.go:88-140`), which first reads all existing `local_state` rows into a map to write only the diff (`store_local_state.go:281-318`). **SIGKILL or restart during the scan starts over.**

**Per-item memory (structs).** `localStateRow` = 3 strings + 6×int64 + bool ≈ 104 B + path (~70 B at this tree's depth) + hash (28 B) ≈ 200 B; held in `currentRows` (map, ~1.5× overhead), then again in the sorted slice, then again in the `buildLocalStateRows` copy, then again in the store's diff map. `hashJob` ≈ 120 B + `fsPath` (~95 B) + `dbRelPath` (~75 B) + `name` ≈ 300 B × 129k. `changeEvent` (`core_types.go:37-69`) ≈ 230 B + strings × 129k. Rough scan-phase peak: 150–250 MB live heap, on top of the remote window if the GC has not yet reclaimed it.

**Plan phase, 138k rows.** `loadCurrentInputsTx` (`engine_current_plan.go:503-571`) holds simultaneously: all `local_state` rows, all `remote_state` rows, filtered copies of both, the planner-visible copies (`replacePlannerVisibleStateTx` **deletes and re-inserts every row into two TEMP tables on every plan**, `store_planner_visible.go:120-175` — ~276k INSERTs per plan), 138k `sQLiteComparisonRow` + 138k `sQLiteReconciliationRow` (`sqlite_compare.go:~675-700`), the observation issues, and a **second full `Baseline`** loaded in the same transaction (`loadBaselineWithRunner`, three maps + `BaselineEntry` ~150 B + strings each; `core_types.go:73-129`). The planner then builds a `pathView` per path with `remoteState`/`localState`/`BaselineEntry` (`core_types.go:426-432`) and one `Action` per reconciliation (`actions.go:52-82`); the dispatch channel is sized `len(plan.Actions)` (`engine_run_once.go:248`). On the first pass with identical content every row is `create_equal` → `baseline_update` (`sqlite_compare.go:525, 625`), which is publication-only: the engine applies them **one `CommitMutation` transaction each**, sequentially, `synchronous=FULL` (`engine_runtime_completion.go:429-453`, `store_write_baseline.go:395-448`, `store.go:97-103`). Those baseline rows survive a kill, so a *second* first-pass only re-hashes files not yet in the baseline (fast path needs ctime+identity, which the mutation takes from the plan's local half, `core_types.go:360-371`).

**Repo-measured cost of the plan queries:** `BenchmarkComparisonQueries` at 100k items, quiet tree, on a 2-core host under modernc SQLite: **23 s** for the two queries per plan (`spec/design/performance-benchmarking.md:653-678`, `sqlite_compare_bench_test.go:12-24`). Expect ~30 s at 138k, plus the TEMP-table rebuild and the baseline reload, i.e. **~40–60 s of SQLite work per plan** on this host — on the first pass and on every later replan (see §9 and finding 6-1).

**Estimates for this host.**
- Remote enumeration: ~700 pages × 0.5–1 s ≈ 6–12 min, ~150–300 MB transient.
- Local scan: stat of 138k entries (each with a `statx` for birth time) ≈ 1–3 min cold; hashing 1.2 TB with 4 readers on the dev host's storage at 150–250 MB/s aggregate ≈ **1.3–2.2 h** (QuickXorHash is pure Go `binary.LittleEndian` arithmetic, `pkg/quickxorhash/quickxorhash.go`, and comfortably keeps up with 200 MB/s on half a core, so the dev host's storage is the bound; four concurrent streams may fall short of the sequential figure, so plan for 2–3 h).
- Plan: ~1 min. Publication of ~138k `baseline_update`s: 138k fsync'd commits ≈ 5–15 min on the SSD.
- **Peak RSS: roughly 0.5–1.2 GB** (live heap 300–600 MB at the plan stage plus GC headroom and SQLite page cache). This is 5–10× the R-6.1.1 target but fits the 3.1 GB currently available. Nothing in the repo measured it (see §12).
- A `sync --dry-run` on this tree performs the *same* full hash scan (`engine_current_plan.go:388-441`) and commits nothing reusable, so budget 2–3 h for it as well.

**Verdict: NEEDS CONFIG / UNKNOWN** — works, but the first scan is a single 2–3 h non-resumable unit; use `included_dirs` staging (§5) to shrink it, and measure peak RSS with `/usr/bin/time -v onedrive-go sync --dry-run` before committing to watch mode.

## 3. Free space (R-6.2.6)

- Measured by `driveops.DiskAvailable` (`statfs`, `internal/driveops/disk_unix.go:23`) on **the parent directory of the download target inside the sync folder**, i.e. `<production sync folder>/...` (`transfer_download.go:732-744`: `checkPath := filepath.Dir(absTarget)`), before `PrepareParent` and before any byte is written (`transfer_download.go:241-249`).
- Two thresholds (`transfer_download.go:762-776`): `available < min_free_space` → `ErrDiskFull` → engine block scope `disk:local` (`scope_key.go:95`) on **all downloads of the mount**; `available < fileSize + min_free_space` → `ErrFileTooLargeForSpace`, a per-file failure. Default `min_free_space = "1GB"` (`config/defaults.go:13`); `0` disables. A `statfs` failure fails open with one Warn (`transfer_download.go:745-760`). ENOSPC/EDQUOT during the write is mapped to the same `ErrDiskFull` (`transfer_download.go:202-216`). The engine keeps `minFreeSpace`/`diskAvailableFn` for start-up revalidation of a persisted `disk:local` scope (`engine.go:66-67, 207-208`). A SQLITE_FULL on the state DB stops the run instead (`store.go:46-59`).
- With 48 GB free and the 1 GB default: downloads proceed; a 12.9 GB file passes (48 > 13.9). The check is per download with no reservation across the 8 concurrent workers, so several multi-GB downloads admitted together can still run the sync volume to ENOSPC (finding 6-8); the failed partial is then removed unless the transfer stalled or was cancelled (`transfer_download.go:628-632`).
- **The trash copy to the SSD does not check the SSD's free space** at all (`detach_unix.go:401-437`, `localtrash.go` has no `statfs`). Failure there is ENOSPC at `io.Copy`/`Sync`, which aborts the delete/overwrite safely (§1).

**Verdict: OK for this deployment** (raise `min_free_space` to ~5–10 GB given the sync volume is full; see §10).

## 4. Dotfiles

- There is **no special handling of `.git`** anywhere (`grep '"\.git"'` hits only `internal/devtool/verify_output_boundaries.go:24`, a repo-tooling constant). `.git`, `.claude`, `.splice` and `.White christmas.mscz,` are ordinary names: `ignore_dotfiles` defaults to false (`config.md:228`) and only then does `hasDotfileComponent` exclude them (`content_filter.go:145`).
- Name validity (`scanner.go:1308-1358`): rejected are empty, invalid UTF-8, control chars, **trailing `.` or space, leading space**, >255 chars, Windows device names, `_vti_`, and the characters `" * : < > ? / \ |`. A **trailing comma is fine** → `.White christmas.mscz,` syncs. `.lock`, `desktop.ini` and `~$` are reserved only for business/SharePoint (`scanner.go:1349, 1430-1440`); on a personal drive `.git/index.lock` etc. are valid and will be observed and uploaded during git operations (write coalescing 500 ms/30 s cap, `observer_local.go:40, 57`).
- `ignore_junk_files` **defaults to true in code** (`config.md:229`, `cli/sync_runtime.go:93 JunkFilesIgnored()`); `docs/configuration.md:105` says `false` — docs lag. Effect (`content_filter.go:250-306`): any component starting with **`.~`**, **`._`**, `.#`, `.Trash-`, equal to `.DS_Store`/`Thumbs.db`/`__MACOSX`/`.Spotlight-V100`/`.Trashes`/`.fseventsd`/`.TemporaryItems`/`$RECYCLE.BIN`, emacs `#x#`, suffixes `.partial .tmp .crdownload .swp .swo .swx ___jb_tmp___ ___jb_old___`, SQLite `<x.y>-wal/-shm/-journal`, and for **files only** (last component): `4913`, **names starting with `~`** (so `~$doc.docx` Office locks) and ending with `~`. Excluded names are invisible on both sides: not uploaded, not downloaded, never deleted — except `*.partial`, which post-sync housekeeping also deletes (§11).
- Of the four named entries, none matches a junk rule (`.splice`, `.git`, `.claude` are not `.~`/`._` prefixed).

**Verdict: NEEDS CONFIG** — add `ignored_dirs = [".git", ".claude"]` (or `ignored_paths = [".git", ".claude"]` to catch them at any depth) unless syncing them is intended; the two dotfiles sync as-is.

## 5. Staged cutover with `included_dirs = ["Pictures"]`

- **Scope rule** (`content_filter.go:105-130`): visible = the included dir itself (as a dir), anything under it, and its ancestor directories. Everything else is invisible to the local walk (`shouldObserveWithFilter` → `skipEntry`, `scanner.go:471-505`, so the 15 other top-level folders are **never walked or hashed** — the first scan covers only `Pictures`) and deletion detection suppresses baseline rows outside scope (`scanner.go:1137-1152`). The remote delta still enumerates the whole drive (delta cannot be scoped) and `remote_state` keeps every item; the filter is applied when planner inputs are loaded (`store_planner_visible.go:78-104`, called at `engine_current_plan.go:530-531`). Nothing is created, deleted or reported for the other folders; `status` simply does not count them. Housekeeping respects the scope too (`stale_partials.go:140-192`).
- **Widening or removing the filter later.** No filter-change bookkeeping exists (`contentFilterConfigsEqual` is used only for shortcut topology, `shortcut_topology.go:142, 346`); the next pass just walks and hashes the newly visible folders and the planner sees rows with `baseline_present = 0`: `create_equal` (both hashes present and equal, or both size 0) → `baseline_update`; otherwise `create_conflict` → `conflict_create_create` → **conflict copy of the local file + download** (`sqlite_compare.go:392-409, 525-526, 625-626`; `planner_actions.go:419-426`). Local-only → upload, remote-only → download. So it merges exactly like a first sync of that subtree; **no resync command is required**. Note `current_equal` is false when either side lacks a hash (R-6.2.11), so a non-empty remote file without a QuickXorHash, or one whose reported hash differs from its served bytes (the iOS HEIC quirk, `transfer_download.go:58-66`), produces a conflict copy on first merge (finding 6-12).
- **R-6.2.1 safety.** A remote delete is planned only from `comparison_kind = 'local_missing'`, which requires `baseline_present = 1` (`sqlite_compare.go:529, 635`). Newly included folders have no baseline rows, so no remote deletes can come from them. **Narrowing** the filter turns previously synced rows into `both_missing` → `baseline_remove` (cleanup only, `sqlite_compare.go:510-512, 606`); nothing is deleted on either side, matching `docs/configuration.md:149-151`. The delete-safety hold (R-6.2.5) additionally caps any surprise.

**Verdict: OK for this deployment** — staging by `included_dirs` is safe with respect to deletes; expect conflict copies where local and remote content disagree (or the remote hash is unusable), not data loss.

## 6. Large files

- **Upload:** resumable session, chunk `ChunkedUploadChunkSize = 10 MiB` aligned to `320 KiB` (`internal/graph/upload.go:10-13`), streamed per chunk with `io.NewSectionReader` (`graph/upload_transfer.go:369-404`); the session record is persisted under `<dataDir>/upload-sessions/` for cross-crash resume (`driveops/session_store.go:22, 98-101`, stale after 7 days line 32; `transfer_session.go:239-247`). The file is **hashed in full before upload** and then read again for the transfer (`transfer_upload.go:254-276`): a 12.9 GB upload costs two full reads.
- **Download of a 12.9 GB file:** `DownloadToFile` (`transfer_download.go:208-281`) writes to `.onedrive-go.<name>~v<12 hex of sha256(remote hash)>.partial` **in the target's own directory** (`transfer_download.go:484-486, 525-540`; names >255 bytes are shortened deterministically), streaming through `io.MultiWriter(file, quickxorhash)` — O(1) memory (`transfer_download.go:612-615`). Interrupted downloads resume by HTTP Range against the same version tag; after a resume the whole partial is re-hashed from byte 0 (`transfer_download.go:566-578, 656-706`). Verify-then-publish: hash mismatch → up to 2 more attempts, then `ErrDownloadIntegrity` and no partial left (`transfer_download.go:379-457`); `finalizePartial` sets mode and **fsyncs**, `ValidateTargetBeforeRename` runs (the trash preservation, §1), atomic rename, directory fsync (`transfer_download.go:286-371`). Stalled transfers (no bytes for 2 min, R-6.8.20) keep the partial.
- `min_free_space` interaction: the pre-check at `transfer_download.go:243` passes for 12.9 GB with 48 GB free; eight concurrent large downloads are each checked independently (finding 6-8). With a replaced target, total traffic for one 12.9 GB re-download on this host ≈ 12.9 GB sync-volume write + 2×12.9 GB sync-volume reads (verify + copy) + 12.9 GB data-filesystem write.

**Verdict: OK for this deployment** (watch SSD usage if large files are frequently replaced).

## 7. What `sync --dry-run` writes, and in-tree artifacts

**Dry-run does not touch the sync folder.** The dry-run pipeline (`runOnceDryRun` → `runDryRunCurrentPlan` → `loadDryRunCurrentObservation`, `engine_run_once.go:191-207`, `engine_current_plan.go:38-57, 388-441`) commits the remote window, findings and the local snapshot to a **scratch SQLite store** in `os.MkdirTemp("", "onedrive-go-dry-run-*")` (`store_scratch.go:63-68`; on this host `/tmp` is tmpfs, so it costs RAM for the duration), plans, and returns via `keepBuiltCurrentPlan` without `commitPendingRemoteObservation`, without executing, and without `postSyncHousekeeping` (`engine_run_once.go:95` requires `executed`). The sync-root token is only written by `commitLocalSnapshot` → `syncTree.MarkRoot()` (`engine.go:334-386`, xattr `user.onedrive-go.root`, `synctree/root_identity_unix.go:51, 162-172`), which the dry-run never reaches; `resolveExpectedSyncRoot` leaves it `bindPending` in memory (`observation_root_identity.go:129-135, 164-189`). Design doc confirms (`spec/design/sync-engine.md:373-380`).

**Dry-run does write, outside the tree:** the state DB with schema + integrity check (`store_compatibility.go:82-100`, `store.go:88-124` → `state_personal_<email>.db`, `-wal`, `-shm`), the root lock `<dataDir>/locks/root-<dev>-<ino>.lock` (`engine_root_lock.go:22, 54-67, 105-108`, never removed by design), control-socket ownership (`cli/sync_flow.go:73-75, 93-97`), refreshed OAuth token file, the configured log file (`cli/root.go:1026`), persisted-scope normalization in the DB (`engine_startup.go:25`), and the tmpfs scratch dir (removed on exit). It also performs the startup drive-identity proof and the full remote enumeration plus the full local hash scan (reads every byte of the tree, relatime only).

**Artifacts a normal sync writes inside the sync folder** (complete list from code):
1. `.onedrive-go.<name>~v<12 hex>.partial` — download in progress, in the target's directory (`transfer_download.go:38-39, 489-493`).
2. `.onedrive-go.<16 hex>.detach` — a file set aside during a verified delete/move-to-trash, same directory, lifetime = hash + cross-FS copy (`synctree/detach_unix.go:29-31, 282-288`); never auto-deleted, reported as `local_interrupted_removal` if left behind (`scanner.go:488-498`).
3. `.onedrive-go.spelling.<…>` — temporary sibling of a spelling-only rename (`content_filter.go:310-319`).
4. `.onedrive-go-restore-*` — only by `trash restore` across filesystems (`localtrash.go:59-60`).
5. `<name>.conflict-YYYYMMDD-HHMMSS` conflict copies (`executor_conflict.go:211`).
6. The extended attribute `user.onedrive-go.root` on `<production sync folder>` itself, written once at the first *live* local-snapshot commit (`engine.go:358`). No marker files.
All of 1–4 are excluded from observation by name (`content_filter.go:137-143`) and `lost+found` plus these artifacts do not count toward delete-safety emptiness (`planner_delete_safety.go:259-272`).

**Would the other client be confused?** By a dry-run: no — nothing appears in the tree. By a live sync running concurrently with abraunegg: yes. abraunegg's default `skip_file` covers `*.partial`, `.~*`, `~*`, `*.tmp`, `*.swp` but not `.onedrive-go.*.detach`, `.onedrive-go.spelling.*` or `*.conflict-*`, so it would upload set-aside files (which can exist for minutes on a 12.9 GB cross-FS trash copy); and onedrive-go's housekeeping deletes **any** `*.partial` in the tree (§11). Never overlap the two.

**Verdict: OK for this deployment** — dry-run is safe while abraunegg still watches; the first live sync must start only after abraunegg is stopped.

## 8. Watch mode on 8,855 directories

- One inotify watch **per directory**, none per file: `AddWatchesRecursive` walks the tree and calls `watcher.Add` for every directory (`observer_local.go:1041-1067`, fsnotify wrapper line 439; new directories are added on create, `observer_local_handlers.go:454, 699`). 8,856 watches against `max_user_watches = 54834` is 16 %, below the 80 % warning threshold (`inotify_linux.go:22, 50-76`); the estimate at startup is baseline folder count + 1 (`observer_local.go:869-879`). One inotify instance per watcher against `max_user_instances = 128`.
- **IN_Q_OVERFLOW** (`fsnotify.ErrEventOverflow`): logged at Info ("too many local changes at once … rescanning"), local truth marked suspect, a recovery full rescan armed after ≥10 s (paced by the last scan's duration, never more than the 5-min safety interval) with exponential backoff on repeats (`observer_local_handlers.go:205-248`, `observer_local.go:46, 751-824`). A full observer channel drops events and arms the same rescan (`observer_local.go:684-713`). The periodic safety scan every 5 min (`observer_local.go:35`) is a full `FullScan` regardless (stat-only via the fast path once the baseline is populated, ~100 MB of transient allocations each time) and re-adds up to 256 missing watches per scan (`observer_local_handlers.go:105-166`).
- **Watch limit hit at startup (ENOSPC/EMFILE/ENFILE/ENOMEM)**: typed `localWatchUnavailableError` → `watchLocalWithFallback` warns once with the sysctl fix, scans at once and then every 5 min, retries the watcher after 10 min doubling to 1 h (`observer_local.go:222-298`, `engine_watch.go:38-40, 441-475`). Hit on a *new* directory mid-session: warn once per cause, existing watches stay, only that folder waits for the safety scan (`observer_local_handlers.go:1308-1335`); only an open-file-limit failure stops watching entirely (`observer_local.go:296-298`). Nothing is silent.
- Sync-root filesystem check via `statfs` treats ext4 as local (`inotify_linux.go:115-145`). kqueue budget code is Linux-irrelevant (`inotify_linux.go:86`).

**Verdict: OK for this deployment.**

## 9. Concurrency defaults on 2 cores

- `transfer_workers` default 8 (range 4–64, `config/validate.go:10-11`): exactly that many worker goroutines, floor 4 (`worker.go:21, 89-113`). `check_workers` default 4 (range 1–16): the `errgroup` limit for scan hashing (`scanner.go:268-269`). No goroutine count scales with tree size; what scales is memory: the dispatch channel buffer `len(plan.Actions)` (`engine_run_once.go:248`), the watch completion buffer 4096 (`engine_watch.go:28`), per-path write-coalesce timers only for paths currently being written (`observer_local.go:88-91`).
- CPU reality on 2 cores: each download hashes its stream, each upload hashes the whole file first, the scan runs 4 hashers, and every plan runs ~40–60 s of single-threaded SQLite (§2). The defaults oversubscribe the box; `transfer_workers = 4`, `check_workers = 2` is the sensible floor (finding 6-10).
- **SQLite:** WAL, `synchronous=FULL`, `busy_timeout=5000`, `journal_size_limit=64 MiB`, `SetMaxOpenConns(1)` (`store.go:97-111`) — one connection per engine, so all in-process DB users (planner read transaction, worker outcome commits, watch batch application) serialize behind each other; a long plan read blocks outcome commits for its duration (latency, not failure). Watch replans are debounced 5 s (`engine_watch.go:22`) and each one reloads all inputs (`engine_current_plan.go:88-104`). `status` while syncing opens a **separate read-only connection** (`mode=ro`, `query_only`, `busy_timeout=1000`, `store_inspect.go:189-197`); WAL readers do not block on the writer and `Close` checkpoints the WAL (`store.go:135-139`). Live owner data (`status --perf`) comes over the control socket instead.

**Verdict: NEEDS CONFIG** (lower both worker counts); correctness OK.

## 10. Logging for production

- `log_file` defaults to `""` (no file); when set, console and a JSON file handler run in parallel (`cli/root.go:1019-1047`), the file level from `log_level` (default `info`), the console from `--verbose/--debug/--quiet`. File is opened `O_APPEND` once at start (`internal/logfile/logfile.go:26-50`). **There is no size- or time-based rotation anywhere in the binary** (`grep -i rotat` finds only comments); `log_retention_days` (default 30) only deletes, *at open time*, files in the same directory whose mtime is older and whose name is the log name, `name.*` or `base-*.log` (`logfile.go:52-106`). A long-running `sync --watch` therefore grows one file without bound until restart; rotate externally (`logrotate` with `copytruncate`, which is safe with `O_APPEND`).
- Info-level content you will see: lifecycle lines (`sync pass starting` `engine_run_once.go:35`, `local observer starting/completed full scan` `scanner.go:116, 203`, `safety scan complete` every 5 min `observer_local_handlers.go:1407`, `worker pool started` `worker.go:110`, `sync store initialized` `store.go:124`), **`fetching delta page` once per delta page at Info** (`graph/delta.go:67` — ~700 lines per full enumeration and at least one per 5-min poll), `remote observer delta enumeration in progress` every 30 s, `deleted stale partial file` (`stale_partials.go:98`), the structured perf summaries (R-6.6.14), and every classified outcome with `run_id`, `action_id`, `condition_key`, `failure_class`, `log_owner`, `drive_id`, `action_type`, `path`, optional `scope_key`, `http_status` (`engine_log_fields.go:19-40`). ## 11. Migration from abraunegg/onedrive

- **abraunegg artifacts inside the folder:**

**Verdict: OK for this deployment, with the operational rule: stop abraunegg before the first non-dry-run sync.**
