## Findings

### MC-1 — The download's file fsync is not covered: removing `f.Sync()` leaves every test green

- **Severity**: medium as a test gap (the code at `26b3bc8b` does fsync; nothing stops a refactor from dropping it, and the requirement R-5.10.1 / D-042 is marked `[verified]` on the strength of this test).
- **Mutation that stayed green** (`internal/driveops/transfer_download.go:362`, in `finalizePartial`):

```diff
-	if err := f.Sync(); err != nil {
+	if err := error(nil); false && err != nil {
 		return errors.Join(fmt.Errorf("flushing the download of %s to disk: %w", targetPath, err), f.Close())
 	}
```

- **Tests run**: `TestDownloadToFile_FsyncsBeforeRenameAndSyncsDirAfter|TestDownloadToFile_DirSyncUnsupportedIsBestEffort` → `ok` (both ran; confirmed with `-v`). Widening is pointless: the `TargetFS` interface (`internal/driveops/transfer_target.go:28-39`) has `OpenFile(...) (*os.File, error)` and `SyncDir(dir string) error`; the file-level `Sync()` happens on the concrete `*os.File`, which no fake can wrap, so no test anywhere in the repo can observe whether it was called. `sync`'s `syncDownloadTarget` (`internal/sync/executor_transfer.go`) returns a `*os.File` from the synctree root too.
- **Why the cited test passes**: `internal/driveops/transfer_manager_test.go:2056-2064`:

```go
func (r *recordingTarget) OpenFile(name string, flag int, perm os.FileMode) (*os.File, error) {
	step := "open-partial"
	if flag == os.O_WRONLY {
		step = "finalize(chmod,fsync)"
	}
	r.steps = append(r.steps, step)
	...
```

  The step name promises chmod+fsync, but it is recorded on the reopen; the assertion at `:2099` (`[]string{"open-partial", "chtimes", "finalize(chmod,fsync)", "rename", "syncdir:folder"}`) therefore proves the ordering of the reopen, the rename and the directory sync, not that the bytes were flushed. The same holds for the chmod.
- **Proposed regression test**: give the fsync a seam the recording target can see, then assert it as its own ordered step.
  1. Add to `TransferManager` an unexported `syncFile func(*os.File) error` defaulting to `(*os.File).Sync` (set in the constructor), and use it in `finalizePartial` instead of `f.Sync()`; add a test-only option (the existing `newTestTM` helper can set it).
  2. In `TestDownloadToFile_FsyncsBeforeRenameAndSyncsDirAfter`, install a recorder that appends `"fsync:<basename>"` to `target.steps` and then calls `f.Sync()`; rename the reopen step to `"reopen-partial"`; assert the exact sequence `["open-partial", "chtimes", "reopen-partial", "fsync:<partial name>", "rename", "syncdir:folder"]`. With the mutation above this fails (`fsync` step missing); with the mutation moved after the rename it also fails (order).
  3. Optionally a second test: `syncFile` returns `syscall.EIO` → `DownloadToFile` returns an error wrapping `"flushing the download"`, the partial is preserved and the target is not created (today no test exercises the fsync-failure branch either).
  The chmod could be recorded the same way (`chmodFile` seam) if D-044's mode handling is to be pinned; it is currently asserted only by `TestDownloadToFile_*Mode*` tests on the resulting file, which is adequate.
