# W48 Definition of Ready: requests that time out count as outage evidence

Worktree `~/src/onedrive-go-wt/timeouts-are-outage-evidence`, branch `fix/timeouts-are-outage-evidence`, base `3a80f900` (#915). Written before any product edit; the new tests of `internal/sync/request_timeout_outage_test.go` were run on the unchanged tree (log `W48-red1.log` in the scratchpad).

## The four questions

**(i) Which scope an answered 504 opens, by which key, and whether a timed-out request carries what the key needs.**
An answered 504 is `serverAnswerServiceOutage` (`domain_graph_error.go:156-157`, any status >= 500). `classifyHTTPResult`'s outage case (`engine_result_classify.go:144-157`) returns `ScopeEvidence = deriveScopeKey(r)` = `scopeKeyForResult(serverAnswerServiceOutage, driveID)` = `SKService()` (`scope_key.go:297-298`), `RunScopeDetection: true`, `TrialHint: trialHintExtendOnMatchingScope`. `UpdateScope` counts it in the service window, 5 unique paths in 30 s (`scope.go:36-37`, `:101-107`), and the crossing failure activates scope `service`. `SKService()` takes no drive, path or status, so a timed-out request carries everything the key needs. An answered 408 is `serverAnswerRequestTimeout`, whose scope key is zero (`scope_key.go:304`): no scope. A timed-out request reaches none of this today: with no status its answer is `serverAnswerNone` (`domain_graph_error.go:108-110`), the request-timeout branch returns no evidence (`engine_result_classify.go:47-54`), and `detectScope` returns early on `HTTPStatus == 0` (`engine_runtime_lifecycle.go:265`). The scope is stored as key `service` and its retry rows as scope_key `service`: a timeout needs no new stored value, so decision (c) does not apply.

**(ii) Every kind of timeout a request can end in, where each is classified today, which reach the request-timeout branch.** Rows of `TestClassifyResult_EveryTimedOutRequestIsOutageEvidenceLikeA504` (all fail today):
- Response-header timeout (`ResponseHeaderTimeout`, 2 min, `graphtransport/profiles.go:14-15,139`): net/http's `errTimeout` answers `Is(context.DeadlineExceeded)` (Go `net/http/transport.go:2933-2935`) -> `isRequestTimeout` -> request-timeout branch: requeue, `request_timeout`, no scope evidence.
- Dial timeout (30 s, `profiles.go:16,141-142`): net's `errTimeout` answers `Is(context.DeadlineExceeded)` (Go `net/net.go:626-634`) -> branch.
- Whole-request deadline: `http.Client.Timeout` (sync's clients set none, `profiles.go:87-98`; the sign-in client sets 60 s, `:79-84`, whose expiry reaches a Graph request's error as "obtaining token", `graph/client_auth.go:155-158`) -> `timeoutError` answers `Is(context.DeadlineExceeded)` -> branch. A request context's own deadline: none exists on an action's path (see iii).
- TLS handshake timeout (15 s, `profiles.go:17,140`): `tlsHandshakeTimeoutError` has `Timeout()` but no `Is` (Go `net/http/transport.go:3385-3389`) -> not `isRequestTimeout`, no status -> `classifyLocalResult` -> `ClassActionable`, no issue type, condition key `unexpected_condition`. Does not reach the branch (row fails on Class: actionable).
- Stalled body read: a transfer's body is watched (`graph/download.go:243,371,436`, `upload_transfer.go:66`), see the next row. A metadata body read has no bound in the transports (`graph/transfer_watchdog.go:16-22`; `profiles.go:139-153` bound dial, TLS, headers, TCP keepalive and HTTP/2 pings only): a live but silent server holds it until the run ends, where it is a shutdown; a dead peer ends it through TCP keepalive (`profiles.go:18-20,143-149`) as a read `*net.OpError` with `ETIMEDOUT` (`Timeout()` true, no `Is`) -> `classifyLocalResult` -> actionable `unexpected_condition`; does not reach the branch (row fails on Class). On HTTP/2 the lost ping closes the connection with an error of no timeout type ("http2: client connection lost"): actionable, not addressed here (only its text names it).
- Stalled transfer: the watchdog's `ErrTransferStalled` (`graph/transfer_watchdog.go:144-157`) -> `isRequestTimeout` -> branch.
Reach the branch today: response header, dial, whole-request, stalled transfer. Do not: TLS handshake, keepalive-ended body read.

**(iii) Which are the service's silence and which the caller's own limit, and how the classifier tells them apart today.**
By `RunEnded` alone: the worker sets it from the context the workers were started under (`worker.go:350`, `runEnded`, `errors.go:172-174`), and the classifier makes a failure a shutdown only when the run ended and the error is the cancellation's echo (`engine_result_classify.go:39-44`); it never reads the error's shape for that. With the run live, no deadline narrower than the run sits on an action's request path: the deadlines made in the non-test files of `internal/sync`, `internal/graph`, `internal/graphtransport`, `internal/driveops` and `internal/retry` are the detached store bounds (`worker.go:255`, `executor_transfer.go:636,670,689`, `engine_retry_trial.go:82`, `engine_shortcut_release.go:668`, `engine_watch_loop.go:389`, `engine_runtime_invariants.go:115`, `store.go:206`) and cleanup bounds after a failure (`graph/upload_transfer.go:336`, `graph/item_create.go:288`, `driveops/transfer_session.go:483,514`); the CLI and multisync put no deadline on a sync run (their deadlines are control-socket, status and close bounds). A command's limit is the run's context ending (a signal's cancel) -> `RunEnded`; a cancel narrower than the run is `context.Canceled` -> `isLiveRunCancel` (`engine_result_classify.go:115-117`), never deadline-shaped. So every deadline-shaped failure of a request while the run goes on is a transport timeout, the service's silence; graph returns the context's cause, not the transport error, only once the request's own context ended (`graph/client_preauth.go:89-98`). The one deadline-shaped failure with the run live that is no request at all is an expired detached store bound: `commitOutcome` (`worker.go:254-259`) and the record of a created item (`executor_transfer.go:636`, whose error fails the upload, `graph/item_create.go:224-227`). The sign-in service's silence (60 s client timeout) is the identity service's, and counts with the Graph service's: no other scope exists, decision (a).

**(iv) What the scope's trial does today when it times out too (by test).**
`TestEngineFlow_ProcessTrialDecision_ATimedOutTrialKeepsTheOutageScope`, unchanged tree: the timed-out trial's decision has `trialHintReclassify` (`engine_result_classify.go:51`) -> `scopeTrialOutcomeRearmOrDiscard` (`scope_lifecycle_policy.go:107-108`): the trial's row is persisted as its own ordinary retry work (unblocked, no scope key) and the service scope, which then holds no blocked work, is discarded. The test failed: "the outage goes on" false, the row's scope key empty, not blocked. With other blocked work left the scope would be rearmed instead; that case is not changed.

**Rider.** `commitOutcome` (`worker.go:254-259`) makes `context.WithTimeout(context.WithoutCancel(ctx), OutcomeCommitTimeout)`. The store has one connection (`store.go:160`); a commit that cannot get it, or a transaction that does not finish, fails with `context.DeadlineExceeded` from `database/sql` (`store_write_baseline.go:418`). `executeAction` sends that error as the completion's (`worker.go:241`), and `isRequestTimeout` (`engine_result_classify.go:47-54,109-111`) gives it requeue with `request_timeout`; after Change 1 it would be outage evidence. The class a failed commit has today: no status and no errno -> `classifyLocalResult` (`engine_result_classify.go:176-215`) -> `ClassActionable` (`resultSkip`), `persistRetryWork`, `trialHintReclassify`, no issue type, condition key `unexpected_condition` (`condition_keys.go:63-87`). That class fits: it is what every other failed commit gets. Proof on the unchanged tree: `TestWorkerPool_ACommitThatOutlastsItsBoundIsAStoreFailure`, which needs one seam (the pool's commit bound as a field, default `OutcomeCommitTimeout`); its result is recorded under item 6.

## Design consequence found while answering (i)

Detection reads the completion's server answer (`scope.go:70`) and `detectScope` skipped a completion with no status, so evidence on the decision alone would not reach the window. The service's silence is therefore placed in the server-answer table (`classifyServerAnswer`: no status and a timed-out request -> `serverAnswerServiceOutage`), with `isRequestTimeout` moved beside it into the domain; the classifier's request-timeout branch takes its evidence from `deriveScopeKey`, the function a 504 uses, and `detectScope` no longer skips a statusless completion. Because the table reads `isRequestTimeout`, the expired store bound is excluded there (the one predicate both the table and the classifier read), so it reaches `classifyLocalResult`, the class of every failed commit, without a second check in `classifyResult`.
