# W5 Definition of Ready: a pending-create record ends once its file can no longer receive this client's upload

Worktree `~/src/onedrive-go-wt/pending-create-lifetime`, branch `fix/pending-create-lifetime`, one commit on `22e88c0b`.

## What I found (checked in code)

- Rows are written in five places: the intent (`RecordPendingCreateIntent`, `uploadNewFile`), the item named by the create hook (`recordPendingCreate`, graph `UploadCreating`, the persisted session's `onCreated`, `recordItemOfFailedSession`), the item named by `claimLostCreate` on a 409, and the item named by observation's claim (`claimIntendedPlaceholderTx`). Rows end in: `placeholderResolved` (content or delete observed), `adoptPlaceholderTx` on a moved path, `claimIntendedPlaceholderTx`'s refused claim, `ClearPendingCreateIntent` (intent only), and the plan-stage prune (intent only). Nothing ends a row naming an item whose file stays empty, whose item the cleanup removed, or that a delete outcome removed.
- (a) A zero-byte create never runs graph's hook, so its row is either an intent (cleared by `clearPendingCreateIntent`, skipped on a canceled context although the create succeeded) or, when watch observation claimed it before the clear, a row naming the item that the intent clear (`item_id = ''`) never deletes. `CommitMutation` touches no pending row. The scenario fake runs the hook for a zero-byte create too (`scenario_remote_test.go:789`), which graph never does.
- (b) `removeCreatedPlaceholder` and driveops `removePlaceholder` only log what `RemoveEmptyItem` reported. `openSessionForUpload` returns a plain error after a failed hook; `persistedSessionUpload` then wraps it in a `CreatedItemError`. `recordItemOfFailedSession` records the item even when graph removed it. graph's `UploadCreating` also hands a cause of `ErrUploadCompletedWithoutItem` (a fragment before the last answered 200 without a body) to the removal, which reads the item back and can delete content that just landed.
- (c) An adopted placeholder whose local file is empty: on a drive with hashes the comparison sees nothing to do, so no outcome commits and the row stays; `followAdoptedPlaceholderTx` then absorbs every later eTag or mtime move.
- (d) `classifyObservedPlaceholderTx` tests `item.Size != 0`; an item of unknown size arrives as size 0 and is read as a stale echo (baseline has content) or adopted (no baseline).
- (e) `followAdoptedPlaceholderTx` returns early on a moved path and leaves the row at the old path; a later create at the old path that meets 409 finishes into the item at its new path. The stale-echo rule finds the row by item ID wherever it sits. An upload by ID into the item is conditional on its eTag only when its session is opened; nothing in the code proves a session already open is refused after a rename, so an upload in flight can commit content into the renamed item, and a window captured before that commit (an eTag moved by the session) then needs the row. Decision: the row follows the item to its new path (on a path already holding a row it stays where it is).
- (f) Code differs from the analysis: graph wraps a final fragment's 200-without-body in `FinalFragmentError` (`upload_transfer.go:393`), so that case goes to `settleUncertainFinalFragment`, which keeps the mark. The defect is on the other branch of `settleUploadedItem`: a completion without the item that is not marked final (a fragment before the last, or an uploader that reports it unmarked) is looked up by ID, and a failed lookup returns a plain `fmt.Errorf` holding the lookup's `ErrNotFound`; `remoteCreateParentGone` reads that as the parent gone and `forgetRemoteItemProvenGone` drops the parent subtree from remote truth. The fix is the Decision's.
- (g) `handleZeroEventPoll` emits nothing. The primary observer's clock is the engine's real clock (`buildRemoteObserver`: `obs.clock = e.wallClock`, which is `e.clock` outside tests). Dispatch has one place (`handleWatchDispatch`) and completions one (`handleWatchActionCompletion`), both on the loop goroutine. An empty batch through `applyRemoteObservationBatch` would still run the findings reconcile (a transaction), so the poll-only batch needs its own branch.
- (h) `finishIntoPlaceholder` tests `item.Size == 0`; a folder or a deleted item of size 0 passes.
