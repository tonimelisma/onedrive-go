# R-5 Transfers

Download and upload transfer infrastructure shared by file operations and sync.

## R-5.1 Parallel Transfers [verified]

- R-5.1.1: The system shall use a flat pool of `transfer_workers` goroutines (default 8, range 4–64) for concurrent file operations (downloads, uploads, deletes, moves, and conflict-preservation work). [verified]
- R-5.1.2: The system shall use a separate pool of `check_workers` goroutines (default 4, range 1–16) for parallel local QuickXorHash computation during filesystem scanning. [verified]

## R-5.2 Resumable Transfers [verified]

- R-5.2.1: When a file exceeds 4 MiB, the system shall use a resumable upload session. [verified]
- R-5.2.2: When a download is interrupted, the system shall resume via `.partial` files and HTTP Range requests on retry. A partial is bound to the remote version it holds (its QuickXorHash, or its eTag for a hashless item, in the partial's name) and is resumed only while the item is still that version and only from a 206 whose Content-Range starts at the partial's length and spans the item's size; anything else discards the partial and downloads from the start. A partial with no version to bind to is never resumed. [verified]
- R-5.2.3: Upload session state shall be persisted to disk and survive process restart. [verified]
- R-5.2.4: Interrupted transfers shall resume automatically on next sync. [verified]
- R-5.2.5: Names the system derives from a user's file name (download partials, conflict copies) shall stay within the 255-byte local name limit, staying deterministic for partials so a download still resumes. A name that is valid locally shall never become undownloadable because of the name the client gives its partial file. [verified]

## R-5.3 Upload Chunking [verified]

- R-5.3.1: Every non-empty upload shall go through an upload session, whatever its size, so its content and modified time land in one version; only zero-byte files use the simple PUT (R-5.6.7). Upload sessions of files above 4 MiB are persisted for resume (R-5.2.3). [verified]
- R-5.3.3: Resumable upload fragment size shall be a multiple of 320 KiB (API requirement). [verified]

## R-5.5 Transfer Validation [verified]

- R-5.5.1: After download, the system shall verify the bytes against API metadata: by QuickXorHash when the item has one (SHA digests are never computed locally and are not comparable), otherwise by size. For a hashless item, an HTML or JSON answer whose length is not the item's size is an error document, never the file; a hashed item is judged by its hash and size alone, so a real `.json` file served as JSON downloads. A download that cannot be verified is retried (3 attempts in all) and then fails with `download_integrity`, leaving the existing local file untouched and no partial behind. An empty item without a download URL is written as an empty file. [verified]
- R-5.5.2: After upload, the system shall verify the stored item against the bytes sent: by QuickXorHash when OneDrive reports one, otherwise by size. A difference is accepted only for the documented Business/SharePoint enrichment class (Office documents and media on a Business or SharePoint drive). Any other difference shall be read back once, and if it persists the upload shall fail: `put`/`cp` exit non-zero, and sync records `upload_verification_failed` and commits no baseline. An upload completion that carries no item shall be resolved by looking the item up, never recorded without identity. [verified]

## R-5.6 Upload Session Robustness [verified]

- R-5.6.1: When an upload fragment returns HTTP 416 (Range Not Satisfiable), the system shall query the session status endpoint for `nextExpectedRanges` before retrying. A network timeout during fragment upload can cause the server to receive partial data without the client ever getting an ACK. Naively retrying the same byte range fails with 416 because the server already has those bytes. The only recovery is to ask the session status endpoint where it actually stopped and resume from there. [verified]
- R-5.6.2: An overwrite by item ID shall be conditional on the eTag the caller's live preflight read: `If-Match` on `PUT /items/{id}/content` and on `createUploadSession` for the item. A remote edit made after the preflight answers 412, which sync treats as a stale precondition and replans, instead of being silently replaced (live probe L-02: Personal honours `If-Match` on both, and a session whose item changes later answers its next fragment with 404). A 412 is never retried without the condition. An older report says some drives change the eTag during session creation itself and answer 412; that is unprobed on Business, and on such a drive the overwrite would replan rather than risk replacing a concurrent edit. [verified]
- R-5.6.3: When an upload session fails, the system shall cancel the session using `context.Background()` to prevent server-side quota leaks. A successful `CreateUploadSession` allocates server-side resources that persist for ~15 minutes and count against storage quotas. If the upload fails, the original context is likely already canceled (that's what caused the failure), so the cancel request must use a fresh `context.Background()` to ensure the cleanup HTTP call actually fires. [verified]
- R-5.6.4: On every drive type, the system shall include `fileSystemInfo` in the upload session creation request to set timestamps atomically and prevent double version creation. Without this, uploading a file and then PATCHing its timestamps in a separate request creates two version history entries per upload, doubling storage consumption. Including `fileSystemInfo` in the session creation sets timestamps atomically with the content in a single version. This is a documented API bug (onedrive-api-docs#877) with no server-side fix, and live probe 7 showed it on Personal too. [verified]
- R-5.6.5: After a zero-byte upload (a create by body, or a simple PUT overwrite), the system shall PATCH `UpdateFileSystemInfo` to preserve the local modification timestamp, which neither request can carry. Because Graph can transiently return `404 itemNotFound`, a 502/503/504 or `409 resourceModified` on that immediate follow-on PATCH even after the upload itself succeeded, the graph boundary shall own a bounded exact retry for those cases (8 total attempts, 250ms base, 2x multiplier, no jitter, 16s max). When the PATCH still fails, the upload shall be reported as uploaded with its modified time not applied, never as a failed upload to send again. [verified]
- R-5.6.6: Upload session fragment requests shall omit the Bearer token. Upload session URLs are pre-authenticated — the credential is embedded in the URL itself. Sending a Bearer token alongside is redundant and dangerous: if the OAuth token expires mid-upload (common for large files), the server rejects the expired Bearer token even though the pre-authenticated URL is still valid, causing spurious 401 errors hours into a multi-gigabyte transfer. [verified]
- R-5.6.7: Zero-byte files shall never use an upload session, which requires at least one non-empty fragment. A new zero-byte file is the empty item the create by body makes (R-5.6.14), with no content request at all (live probe L-01); a zero-byte overwrite is a simple PUT by item ID. [verified]
- R-5.6.8: The system shall not re-query file metadata immediately after upload. After upload completion, server-side processing (virus scanning, indexing, SharePoint enrichment) can temporarily show incorrect size and hash values. The upload completion response itself contains the correct metadata. Querying the item endpoint immediately can return stale pre-processing values, causing false hash mismatches and unnecessary re-uploads on the next sync cycle. The one exception is R-5.5.2: an item that does not match what was sent, or a completion that carried no item, is read back once. [verified]
- R-5.6.9: Only an overwrite by item ID shall pass `@microsoft.graph.conflictBehavior=replace`; by then the sync engine has decided to overwrite that item, and R-5.6.2 makes the overwrite conditional. A new file shall never be created with `replace` (R-5.6.14). [verified]
- R-5.6.10: ~~Simple-upload create replay after a session-route `404`~~ [canceled — non-empty creates no longer use the simple-upload route (R-5.3.1); the fresh-parent `404` window is covered by the upload-session create retry alone]
- R-5.6.11: Resuming an upload session shall keep the session URL when Graph's session status response omits `uploadUrl`, which it always does, and send only the byte ranges Graph still expects. [verified]
- R-5.6.12: An upload whose final fragment failed, or whose recorded session is gone on resume, shall look the item up before uploading again and adopt it only when it is provably the upload's commit: a matching QuickXorHash, or, for a hashless or Business-enriched item, the modification time the upload sent together with an eTag other than the planned one. A failed lookup is retried, never read as an invalidation. A session that is gone before its recorded expiry while the item holds other bytes was invalidated by a concurrent change (live probe L-02): the upload shall fail as stale (sync re-observes and replans) rather than restart. A recovered `nextExpectedRanges` offset past the end of the file is an error. [verified]
- R-5.6.13: Whenever a persisted upload-session record is dropped (content changed, resume failed), its server session shall be canceled best-effort on a context detached from the caller's. [verified]
- R-5.6.14: A new file shall be created with its name in a JSON body (`POST /items/{parent}/children` with `"file": {}` and `@microsoft.graph.conflictBehavior=fail`) and its content then sent by item ID through an upload session conditional on the created item's eTag. No user-supplied name shall appear in a create or upload URL: Graph's router reinterprets some (live probe 4: `v1.0` became folder `_api` holding `v2.0`), and path routes cap names near 291 characters (L-05). A name that already exists, including a spelling OneDrive treats as the same, shall fail with a conflict rather than be replaced. When the content step fails before its final fragment, the empty item shall be deleted again if a read-back shows it still empty, conditional on the eTag just read: an upload session opened on the empty item moves its eTag although no content landed. Live probe L-01: the create plus a session on the item make one version. [verified]
- R-5.6.15: A new file's empty item (the create by body, or the visible 0-byte item a path-routed upload session makes, L-34) shall be recorded durably before its content is sent, with its item ID and creation eTag. While that item is still empty it is this client's placeholder, whatever its eTag (opening and canceling an upload session on it moves the eTag without content; e2e `TestE2E_SyncWatch_FileModification`): a later pass shall upload into it by ID with If-Match on its current eTag (or delete it with If-Match when the local file is gone), never treat it as a remote file to download or a create conflict; an observation of that empty state after the upload committed is not a remote change; a retry of the create that meets it with 409 uploads into it; and a failed upload whose final-fragment lookup shows the content did not land deletes it at once if still empty, conditional on the eTag that lookup read. Every lookup of an upload's outcome after the create uses the created item's ID. A create refused because OneDrive holds a differently spelled sibling of the same name is a durable name-collision condition naming both names, held with backoff. [verified]

## R-5.7 Upload Size Limits [verified]

- R-5.7.1: The system shall reject uploads exceeding the 250 GB maximum file size before hashing or attempting any network transfer. [verified]

## R-5.8 iOS Media Handling [verified]

- R-5.8.1: When downloading iOS `.heic` files whose API-reported size/hash does not match the actual downloaded bytes (known API bug), the system shall accept the download rather than failing validation. A size mismatch identifies the quirk, so the first download is accepted without hash retries; the known condition is logged at DEBUG, not as a per-photo warning. [verified]
- R-5.8.2: Download bytes that differ from OneDrive's metadata shall be accepted only as a known, deterministic server transform: the iOS HEIC quirk, or the same bytes at the reported size on every attempt (P-10). The baseline then records OneDrive's reported hash as the remote side and the bytes' hash as the local side, so the next pass neither downloads nor uploads the file. [verified]

## R-5.10 Download Write Path [verified]

- R-5.10.1: A download shall be durable before it is reported: the partial's bytes are flushed to disk (fsync) before the rename, and the target's directory is flushed after it, so a power cut cannot leave an empty or zero-filled file that the baseline already records as synced. [verified]
- R-5.10.2: A download that replaces a file shall keep that file's permission bits (never setuid, setgid or sticky); a new file shall get 0666 minus the umask and a folder the CLI creates 0777 minus the umask. Partials stay 0600 while they are written. [verified]
- R-5.10.3: A sync download shall write only inside the sync root and shall never create a parent folder: a parent that is missing or no longer a folder makes the download a stale precondition. CLI `get` creates missing parents. [verified]

## R-5.9 Download Routes [verified]

- R-5.9.1: A file whose metadata has no pre-authenticated `downloadUrl`, or whose freshly refetched `downloadUrl` is refused again, shall download through the bearer-authenticated `GET /items/{id}/content` route (tempauth URLs retire on 2027-04-01). The bearer goes only to Graph: the client does not follow the redirect itself, validates the target as a Microsoft content host, and fetches it without an `Authorization` header (live probe L-20 showed the content host needs none). The authenticated leg gets the same 401 forced refresh as every Graph request. Resume offsets carry over as `Range`, and a resumed answer must be 206 with a `Content-Range` starting at the offset; a full-body 200 is refused, never appended. Folders and OneNote packages still report that they have no content. [verified]
