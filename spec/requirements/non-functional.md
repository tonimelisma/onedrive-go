# R-6 Non-Functional

Performance targets, data integrity, process model, safety, observability, and packaging.

## R-6.1 Performance Targets [target]

- R-6.1.1: Memory usage shall stay below 100 MB for 100K synced files. [target]
- R-6.1.2: CPU usage in idle watch mode shall stay below 1%. [target]
- R-6.1.3: Initial sync of 10K files shall complete in under 10 minutes. [target]
- R-6.1.4: Startup time shall be under 1 second. [target]
- R-6.1.5: Binary size shall be under 20 MB (single static binary, no runtime dependencies). [target]
- R-6.1.6: When operating in production, the system shall meet CPU, memory, and I/O performance targets validated via repo-owned profiling and benchmark scenarios. [planned]
- R-6.1.7: The repository shall define stable named representative benchmark scenarios, starting with a harness-validation startup scenario and one canonical live bidirectional catch-up workload before broadening coverage. [planned]
- R-6.1.8: Representative benchmark runs shall record both external process metrics (for proof) and repo-owned internal perf/timing metrics (for explanation) in machine-readable artifacts. [planned]
- R-6.1.9: Publicly reported representative performance numbers shall be generated from repo-owned benchmark artifacts and accompanied by machine/date/methodology and subject-under-test context. [planned]
- R-6.1.10: Cross-app comparison results shall use documented fixtures and methodology, and shall not be mixed into required per-PR verification claims. [planned]

## R-6.2 Data Integrity [verified]

The system shall never silently lose or corrupt user data. This umbrella principle is enforced by the following specific safety invariants:

- R-6.2.1: (S1) The system shall never delete a remote item based on local absence unless a synced baseline entry exists. [verified]
- R-6.2.2: (S2) The system shall never process deletions from an incomplete enumeration (partial delta fetch or unmounted volume). Absence shall mean absence from what an enumeration returned: an item the client chose not to convert is not absent, a shared-folder item missing from one listing shall be confirmed gone by a live lookup before its local copy is deleted, and a shortcut placeholder missing from one complete listing shall be confirmed removed before its local projection is drained. [verified]
- R-6.2.3: (S3) Downloads shall use atomic file writes (client-owned namespaced partial + hash verify + rename). [verified]
- R-6.2.4: (S4) Local deletions shall verify the file against the baseline before deleting: by content hash when the baseline records one, and otherwise by the baseline's recorded size and mtime. A content hash that no longer matches is a proven change to the file: its baseline row shall lose its recorded inode change time, so the next scan reads the file instead of trusting the row (R-2.2.4) and plans the change as the local edit it is. On mismatch, or when the baseline records neither hash nor size, the local content shall be preserved and the path replanned rather than deleted unverified. [verified]
- R-6.2.5: (S5) Delete safety protection shall prevent mass accidental deletions in either direction. When one side's complete observation has no entries while the baseline holds files, or when the deletes (files and folders) toward one side, counted together with the unconfirmed deletes already run toward that side in the preceding 24 hours, exceed max(50, 30% of the synced items as they stood before those), the system shall hold those deletes, and every action that depends on them, for confirmation; a delete toward OneDrive of a recorded mount point (R-6.2.15) whose folder is missing from the local side, or of anything below it, shall be held however few such deletes there are; moves shall not count, and `lost+found` and the client's own artifacts shall not make a side non-empty. One-shot and watch mode shall continue all other work, `status` shall show the held deletes, and `sync --confirm-deletes` shall apply exactly the recorded held set; deletes that appeared since are judged by the hold again, and the confirmed deletes, with those run before them toward the same side, no longer count toward it. [verified]
- R-6.2.6: (S6) Before each download, the system shall verify available disk space. When below `min_free_space`: set a `disk:local` block scope on all downloads. When above `min_free_space` but below file size plus `min_free_space`: record a per-file failure. [verified]
- R-6.2.7: (S7) Client-owned transfer partials shall never upload. When `ignore_junk_files` or explicit path filters exclude arbitrary partial or temporary files, the system shall not upload or download them. Transfer-artifact cleanup shall respect configured include/ignore boundaries and protected child roots. [verified]
- R-6.2.8: File operations (ls, get, put, rm, mkdir, stat, mv, cp) shall work independently of sync state — no sync database involved. [verified]
- R-6.2.10: When a transfer connection stalls without context cancellation, the system shall enforce a per-transfer timeout or connection-level deadline to prevent indefinite hangs. [verified]
- R-6.2.11: (S9) The system shall never conclude that a local and a remote copy hold the same content without comparing content hashes from both sides. When either side has no hash, equal size shall not be treated as evidence of equality, and the paths shall be reconciled rather than recorded as agreeing. [verified]
- R-6.2.12: (S10) Each sync state shall be bound to the identity of the local sync folder it was built from, recorded in the same transaction as the first committed local snapshot: a random token stored as an extended attribute on the folder where the filesystem supports one, otherwise its inode and filesystem, and its birth time where the filesystem records one, so a folder re-created at the sync path that got the old inode number back is still a different folder. When the folder at the sync path no longer matches (replaced, recreated, an unmounted disk's empty mount point, a root symlink re-pointed elsewhere), or when a state with synced items has no recorded folder, the system shall refuse to scan or plan that drive, naming `drive rebind-root` as the explicit way to accept the folder, which shows the remembered and present file counts and asks for confirmation. [verified]
- R-6.2.13: (S11) A read failure on the sync folder itself shall stop the scan as an unavailable sync folder; it shall never be recorded as a read boundary that covers no path, which would make every synced file look deleted. [verified]
- R-6.2.14: (S12) A synced path whose item the scan cannot represent shall be unavailable local truth, never a delete: a path now occupied by a symlink sync does not follow or by a FIFO, socket or device; a synced item renamed to a name OneDrive refuses, a path too long, or an excluded name such as a dotfile (recognised by its filesystem identity); an entry the scan listed but could not stat; and a file whose content could not be read. For a folder this covers its whole subtree. The user sees one condition per path naming what happened, and the condition clears on the next full scan that finds an ordinary file or folder at the path, which then syncs again. [verified]
- R-6.2.15: (S13) Local observation shall not cross into a folder that is the mount point of another filesystem unless `cross_filesystems = true`; the mount point is a read boundary, so nothing beneath it is uploaded, downloaded into, or deleted on either side. A mount point crossed under `cross_filesystems` shall be remembered, and when it is later found on its parent's filesystem, its content shall be unavailable truth rather than deletions; `drive rebind-root` keeps recorded mount points, the deletes of a recorded mount point whose folder is missing are held for confirmation whatever their number (R-6.2.5), and a recorded mount point is forgotten only once its folder is neither synced nor present, or by the user's `drive forget-mount` (R-6.2.18). A mount point that is not crossed is a boundary only while a scan finds it one: when the folder is back on its parent's filesystem (the disk was unmounted, or the folder was never a disk again), the next full scan clears the condition and the folder syncs as an ordinary folder. [verified]
- R-6.2.16: (S14) A path the planner's decision table does not classify, a plan that would transfer a folder as file content, and a planned action whose type or folder create side is outside its enum shall stop that drive's sync pass before any of its actions run, with an error naming the path (for an unclassified path also its kinds and the decision inputs no rule matched). The system shall never plan such a path as nothing to do or drop it from the plan, because a path planned as nothing silently stops syncing. In watch mode the drive's runner ends with the error and is restarted after the R-2.8.11 backoff. [verified]
- R-6.2.17: (S5) A user shall confirm held deletes (R-6.2.5) without stopping a running `sync --watch`. While a watch runs, `sync --confirm-deletes` shall show each selected drive's held set, with a count and a token derived from exactly those deletes, and the command that confirms that set, and shall confirm nothing; `sync --confirm-deletes --held-set <count>-<token>` shall confirm that set to the running watch through its control socket, and the watch's next pass shall apply exactly that set. A confirmation of a set other than the one the drive holds when the watch takes it (a delete held or released after the user looked) shall be refused, say so, and confirm nothing; deletes held after the confirmation are judged by the hold again. [verified]
- R-6.2.18: (S13) A user shall be able to forget one recorded mount point (R-6.2.15) whose folder now holds the disk's content as a plain folder of the sync folder's own disk, with `drive forget-mount <path>`: after a typed confirmation or `--yes`, it removes that one record and nothing else, so the next sync compares the folder's content with OneDrive as ordinary local truth and deletes nothing. It shall refuse, changing nothing, a folder that is not recorded, is missing, holds no files, is still on another device, or is outside the sync folder, and shall refuse while a sync owns the drive. [verified]

## R-6.3 Process Model [verified]

- R-6.3.1: Only one sync process per configuration shall run at a time. [verified]
- R-6.3.2: Status and query commands shall be concurrent-reader safe while sync is running. [verified]
- R-6.3.3: The system shall enforce single-instance ownership via the Unix control socket. [verified]
- R-6.3.4: Concurrent and runtime components shall document the single owner of mutable state, goroutines, channels, timers, and mutex-guarded fields. [verified]
- R-6.3.5: Runtime-critical mutexes shall document the fields they guard, and any intentional nested lock ordering shall be called out in code comments or the governing design doc. [verified]
- R-6.3.6: Every command, not only `sync`, shall treat the first SIGINT/SIGTERM as a cooperative shutdown that cancels the command context so in-flight work unwinds through its own cleanup, and shall treat a second signal as an immediate exit. The signal handler shall be released when the command completes. [verified]
- R-6.3.7: `sync` (one-shot and `--watch`) shall refuse to run with effective UID 0 unless `--allow-root` is given, as a usage error (exit 2) before reading config or touching any folder, because a root sync leaves root-owned files the user cannot change. With `--allow-root` it runs and warns once. [verified]
- R-6.3.8: A watch mount shall fail rather than run blind. A panic in any goroutine the mount's watch runtime owns (a local or remote observer, the full remote refresh, the socket.io wake source, or the per-mount runner itself) shall fail that mount only: the panic and its stack shall be logged, every other mount and the process shall continue, and the mount shall restart with the usual backoff. Losing the mount's last observer outside shutdown shall fail the mount too, since a watch that observes nothing would read healthy while syncing nothing. [verified]
- R-6.3.9: A sync shall not wait without bound for a drive to stop, whatever stops it (a reload, a drive removed or paused, a shortcut retired, a drive that exited, shutdown, the end of a one-shot pass). Every store write an engine runs detached from cancellation shall carry a deadline. A drive whose sync has not returned within its stop bound (one detached store write's bound plus a margin), or whose sync state has not closed within the close bound, shall be logged at Error with every goroutine's stack, shall never have its state closed, acknowledged, cleaned up or replaced under it, and shall end the command with exit status 1, also when a user asked for the stop. An event from a drive's runner shall change nothing once that runner has been stopped or replaced. The watch shall keep its owner lock until every drive has stopped, `drive reset-sync-state` and `drive rebind-root` shall refuse while any engine holds the drive's sync folder or its state store, and `drive remove --purge` and `logout --purge` shall delete a drive's state store only after its config section is removed and a running watch was told, never while an engine still has the store open: such a store is kept and the command names how to finish. [verified]
- R-6.3.10: No goroutine shall end the process with Go's exit status 2. Every goroutine product code starts shall recover a panic at its boundary, and every recover shall log the panic once, at Error, with the stack of the goroutine that panicked (`internal/panicguard`; a scan of every product package enforces both). A panic outside a drive's own runtime (the watch control loop, the control socket server, the config file watcher, an engine's close, the systemd watchdog keepalive, the signal handler, the performance logger, or the command's own goroutine) shall end the command with exit status 1, also when it ended a stop the user asked for or travels with a sign-in or configuration failure; the work it interrupted (a request, a wait, a sync action) shall end as at a stop; `sync --watch` shall stop its drives first and leave the failure as its final `STATUS=`, and the error the command prints shall carry the stack, because a command run without a log file has nowhere else to keep it. A panic in a helper of a unit whose failures are already reported one by one (a drive or shortcut of a one-shot pass, an account's drive listing, a file of a `get`, a shared item's lookup, the sign-in callback) shall be that unit's failure, reported the way its other failures are; a one-shot pass whose control server panicked finishes its pass, as when the server stops on its own. A panic in a timer callback, which runs on a goroutine of its own, shall end the drive's run in which it fired as that drive's failure, with the actions in flight ending as at a stop so that the next run redoes them, and a panic in a transfer's stall timer shall fail that one transfer. [verified]

## R-6.4 Safety [verified]

- R-6.4.1: Local deletions triggered by remote absence shall verify the on-disk file hash against baseline before deleting. On mismatch, the system shall preserve the newer local content and let the next plan recreate the remote item instead of silently deleting it. [verified]
- R-6.4.2: Deletion safety shall be both per-item (each delete verified against the synced baseline) and batch-level (the delete-safety hold of R-6.2.5). A held delete shall be released only by an explicit user confirmation, never by a timer or retry. [verified]
- R-6.4.3: The delete-safety thresholds shall be fixed policy rather than configuration; delete-threshold keys in the config file shall be rejected as unknown configuration rather than silently ignored. [verified]
- R-6.4.4: Remote deletions shall go to the OneDrive recycle bin by default. [verified]
- R-6.4.7: The system shall support configurable disk space reservation (`min_free_space`, default 1 GB). When available space falls below this threshold, downloads shall be scope-blocked. Set to 0 to disable. [verified]
- R-6.4.8: All local filesystem writes shall be confined to the sync root directory. The executor, and `trash restore` for everything it changes in a sync folder, write only through the rooted `synctree` capability, which refuses traversal, absolute paths and symlinked components that would leave the root, to prevent escape from path reconstruction bugs. A rename that must not replace its destination (the local move's, the conflict copy's, the trash restore's, and each of the two steps of a spelling-only rename) shall be one operation on descriptors of its parent folders, every one inside the sync folder opened through the root, so a folder swapped for a symbolic link out of the root at any moment fails it instead of carrying it outside, and no step shall check for the destination and then rename over it. Inside the sync folder such a rename never copies the entry: where the system offers neither the no-replace flag nor a hard link for the entry, it is a check of the destination and then a plain rename, an exception to that rule; when the sync folder's filesystem offers neither for any file (FAT-family), the engine shall warn once as it starts, naming the sync folder, that a save landing while sync puts a file back can be replaced. The other exception is a spelling-only local move whose no-replace rename finds the destination taken and a check finds it naming the source itself: it is then a plain rename, because on a volume that folds case the destination is the source, which a no-replace rename finds taken (`spec/design/sync-execution.md`, local move). A local move that replaces its destination first takes the file there out of the sync folder by the local delete rule, verified through the descriptor of the inode that leaves, so its rename replaces nothing. A file moved into a sync folder from outside it (the trash restore) shall be refused when the folder it lies in is the sync folder or below it, decided by the device and inode of the opened folders and not by the path's text, and a file taken or copied out of a sync folder (into the trash) shall be refused a destination inside it, decided the same way on the one descriptor of the destination's folder, opened without following a symbolic link in its own name, that every step of the move or copy is then made on, so a folder swapped for a link meanwhile fails it instead of redirecting it, and no step shall replace what it finds at the destination's name. A failure inside the sync folder without the errno of a missing name shall never read as absence, and ENOTDIR shall read as absence only when a lstat through the root agrees. [verified]
- R-6.4.9: Every local file the sync deletes, and the previous version of every local file a download replaces, shall be kept in a per-drive trash under the data directory for 30 days rather than destroyed, removed from or preserved by the exact inode that was verified and only while it is unchanged since verification, and recoverable with `onedrive-go trash list`, `trash restore` (which never overwrites, save for R-6.4.8's one exception, never writes through a symbolic link, and never re-creates a sync folder that is gone) and `trash empty --confirm`. A crash at any point shall leave the file recoverable: an entry is recorded before the file moves, uncommitted files are never purged automatically, and a file left set aside inside the sync folder is never deleted and is reported until the first full scan that no longer finds it. The trash is the one place sync writes local content outside the sync root (R-6.4.8). [verified]
- R-6.4.10: Managed state files (config, tokens, upload sessions, logs) shall be read and written only through a capability rooted at their folder: every open, removal, rename, temporary file and directory creation beneath that folder shall resolve inside it, and a name that leads outside it, through `..` or a symbolic link pointing elsewhere, shall fail without creating, changing or removing anything outside. A temporary file shall never open or replace an existing entry. A failure shall read as absence only when the name is absent: never for a name that leads outside the folder, and never for a create refused for lack of permission or space or by a read-only filesystem. Nothing can be beneath a file: a name whose folder, or any folder above it, the managed folder included, is a file shall read as absent, while listing a folder that is a file shall fail as not a directory. Whether the managed folder is a directory shall be known before it is opened, so a managed folder that is a FIFO or another special file answers at once instead of blocking. The sync state database is outside this requirement: SQLite opens it and its `-wal` and `-shm` files by path, so only the creation of its folder goes through the rooted capability. [verified]
- R-6.4.12: A shortcut child mount's local trash shall belong to its parent drive: `trash list --drive <parent>`, `trash restore` and `trash empty` shall cover the parent's own trash and the trash of every shortcut child of that drive (each entry naming the sync folder it came from), the parent's housekeeping shall expire the children's committed entries after the retention like its own, and the removal of a child's state shall first move every entry of its trash, committed, pending or orphan, into the parent's trash with its ID, time, reason and state. The move shall never delete an entry: at every moment an entry is in exactly one of the two trashes, a crash leaves the rest for the next attempt, and a move that fails keeps the child's trash and its state and is reported as a cleanup failure the parent publishes again. [verified]
- R-6.4.13: A file the release of a removed shared folder puts in the trash shall be recorded with the reason `released`, which `trash list` words as its shared folder having been removed from this account and `--json` carries as `released`; how `trash list` words a reason shall be an exhaustive switch over the declared reasons, and an entry with a reason outside that set shall still be listed with its stored word. A restore whose sync folder is gone, such as a released shared folder's, shall not create it again and shall name where the file is in the trash. [verified]

## R-6.5 Crash Recovery [verified]

- R-6.5.1: The sync state store shall provide durable, transactional writes that survive process kill. [verified]
- R-6.5.2: Every sync operation shall be atomic — incomplete operations shall not corrupt state. [verified]
- R-6.5.3: On startup, the system shall rebuild runnable state from durable snapshots, `retry_work`, `block_scopes`, and `observation_state` rather than relying on persisted in-flight action flags. [designed]
- R-6.5.4: Atomic managed-file writes shall fsync the directory the rename landed in, so the renamed entry is durable and not only the file contents. A write whose durability cannot be established shall report an error rather than claim success, except on a filesystem that cannot fsync a directory at all (it answers `EINVAL`, `ENOTSUP` or `EOPNOTSUPP`, as FUSE and SMB mounts do), where the file's own bytes are synced and the directory sync is best effort. [verified]

## R-6.6 Observability [verified]

- R-6.6.1: The system shall support dual-channel logging: console (stderr) and log file. Every command writes to the configured log file, including commands that do not need a drive, and records logged while the config file is being found reach it too. [verified]
- R-6.6.2: Console verbosity shall be controlled by `--quiet`, `--verbose`, and `--debug` flags. [verified]
- R-6.6.3: Log file level shall be controlled independently by `log_level` in config. [verified]
- R-6.6.4: The log file shall use structured JSON format. [verified]
- R-6.6.5: The system shall support progress bars and color-coded transfer output. [future]
- R-6.6.6: The system shall support a TUI (terminal UI) for real-time status. [future]
- R-6.6.7: A group of more than 10 items of one kind in a pass shall be logged as one summary line with the count, each item at DEBUG, at the level its kind calls for. Newly skipped files that share one issue type are one WARN line naming up to three sample paths; a group of 10 or fewer warns once per file, and a file already recorded stays at DEBUG. Failures kept as retry work are one INFO line per `condition_type` (R-6.6.12), never WARN, because the sync console reports each failed file (R-6.6.18). [verified]
- R-6.6.8: A single failed attempt of a transient request shall retry silently (DEBUG). When a second consecutive attempt also fails because OneDrive is unreachable, the system shall announce it once per outage at WARN with the cause and the next retry delay in human units, however many requests are in flight; the announcement re-arms once OneDrive answers again. Further attempts log at DEBUG. A retry wait of 10 s or more (rate limiting, `Retry-After`, long backoff) shall be announced once per throttling episode at WARN; shorter waits stay at DEBUG. A wait the transport does not start because it would end after the request's deadline (R-6.8.8) is not announced. The final outcome is the returned error, reported once by the command; the transport does not log it again above DEBUG. [verified]
- R-6.6.9: When transient errors resolve within the retry budget, the system shall log at INFO with attempt count (not WARN). [verified]
- R-6.6.10: When retries are exhausted, the system shall log a single WARN with final error, attempt count, and next retry time. [verified]
- R-6.6.11: Every failure shown to the user shall include a plain-language reason and a concrete user action. Per-error-type reason and action text shall cover all failure categories (quota, permissions, disk space, service outage, rate limiting, naming violations, case collisions, network errors, auth failures, unknown errors), with drive-aware variants where the affected configured drive matters. A 501 Not Implemented from OneDrive is a refusal, not an outage: the system shall pass on OneDrive's message instead of calling it a temporary server problem. A command that another sync owner blocks shall refuse before announcing any work. [verified]
- R-6.6.12: When more than 10 failures of the same `condition_type` are kept as retry work within a single sync pass, the system shall aggregate them into a single summary INFO log line with count, logging individual paths at DEBUG. The per-file report of each failure is the sync console's activity line (R-6.6.18), so the engine's summary shall not repeat it at WARN. [verified]
- R-6.6.13: Classified sync outcome logs shall emit a stable structured schema. Every classified sync log line shall carry `condition_key`, `failure_class`, `log_owner`, `scope_key`, `path`, and `run_id`. Result-path logs shall also carry `drive_id`, `action_type`, and `action_id`, with `http_status` and `trial_scope_key` added when applicable. The schema is for the log file and `--verbose`/`--debug`: default-verbosity console lines show only `path` of these fields. [verified]
- R-6.6.14: The system shall emit structured INFO-level performance summaries for CLI commands, kept in the log file at its default level and shown on the console only with `--verbose`/`--debug`. Long-running one-shot commands shall emit periodic progress summaries, and watch owners shall emit interval summaries, using stable aggregate fields only. Always-on performance logs shall omit raw paths, account emails, drive IDs, item IDs, and transfer URLs. [verified]
- R-6.6.15: The system shall expose live sync-owner performance snapshots through `status --perf` and the local control socket. This live performance surface shall be ephemeral only: when no owner is active, the system shall report unavailability instead of fabricating durable history. [verified]
- R-6.6.16: The system shall support explicit opt-in performance capture from the active sync owner, writing a local bundle with CPU, heap, block, mutex, goroutine, and optional trace artifacts. Full per-mount detail is allowed only in the explicit capture bundle; always-on logs and status surfaces remain redacted aggregates. [verified]
- R-6.6.17: The live perf snapshot, structured perf logs, and `status --perf` shall expose path-free aggregate stale-work observability: superseded counts by owning boundary, scoped local-observation commit counts, suspect-local-truth recovery counts, and worker-idle duration by replan phase. [verified]
- R-6.6.18: `sync` and `sync --watch` shall print one line per finished user-visible file action at default verbosity — download, upload, local delete, delete on OneDrive, move, folder create, conflict copy — naming the path relative to the sync folder, with the size for transfers. Successful actions go to stdout; failures that need the user go to stderr with a plain reason; failures kept as retry work are shown only with `--verbose`. `--dry-run` lists each planned action the same way ("Would download …"). [verified]
- R-6.6.19: One-shot `sync` shall announce what it is about to sync (folder and account) before work starts, and end each drive with one summary line in human units ("Done in 5.6 s: downloaded 19 files (300 MB), created 2 folders.", "Up to date (1.6 s).", "Dry run, nothing was changed. Would …"), plus a line naming work a one-way mode held back. A delete is counted by what it removed, files and folders apart ("deleted 3 files and 1 folder locally"), in the live summary, the dry run and the `--json` summary (`folder_counts`), and a deleted folder's own line marks it as a folder. The summary shall count what the run did, not what it planned: with the activity feed wired, a pass that did nothing says so, and a retry the run itself completed in a later pass is not promised again. A drive that left work (R-6.6.28) says so in its summary line, by what a later run or the user can finish as the run's last pass ended, each file once: how many failed, how many will be retried on the next sync, and how many are still not synced because of an issue `status` lists; a file an earlier pass failed and a later pass of the same run finished is in none of them, and such a drive is never "Up to date". [verified]
- R-6.6.20: Watch mode shall print a startup line per watched folder and account, a stop hint when attached to a terminal, "Stopping…" on the first signal and "Stopped." on a clean exit. Activity lines are prefixed with the time of day except when writing to the systemd journal. [verified]
- R-6.6.21: The console shall be human text. With the default `log_format = "auto"`, the default console shows notices, warnings and errors: warnings render as "Warning: <message> (details)", a notice (the all-clear after a warning) as a plain line, with no level keys, and an error value as its plain reason rather than its wrap chain; in a `sync --watch` on a terminal these lines carry the watch's own `[HH:MM:SS]` stamp, otherwise no timestamps; `--verbose`/`--debug` add timestamped key=value detail; when stderr is the systemd journal (`$JOURNAL_STREAM` matches stderr), lines carry `<N>` syslog priority prefixes and no timestamps. JSON on the console only with an explicit `log_format = "json"`; the log file stays JSON. A clean shutdown shall produce no warnings. [verified]
- R-6.6.22: A command error shall be printed exactly once. Errors a user can fix shall be one plain line with the action: sign-in problems name the login command, unreachable-network failures say so and name the concrete cause, as do timeouts, TLS failures and dropped connections, whether before or while OneDrive answers (HTTP/2 stream resets included; an answer that went silent mid-body reads as not answered in time and a connection whose health check went unanswered as interrupted, each known by the Graph client's type, not its text), and each names the service whose request failed: Microsoft sign-in for a token refresh or a login request, OneDrive otherwise; an expired or declined sign-in code says to run `login` again; the full error chain is shown with `--verbose`/`--debug`. With several drives, each drive's error is printed under its name and the command error only counts them. [verified]
- R-6.6.23: A saved login Microsoft rejects at token refresh (OAuth `invalid_grant`: expired, revoked) shall be presented as "sign-in required" in `status`, `sync` and every command, distinctly from a request OneDrive rejected with a valid login. [verified]
- R-6.6.24: `login` shall show the code, where to enter it, which account to sign in as, when the code expires, a hint for passkey sign-ins that end on an error page, and that it is waiting; on success it shall say where files will sync and what to run next, without internal identifiers. [verified]
- R-6.6.25: `drive list` and `status` shall derive a configured drive's state the same way, so they never disagree (a drive with recorded issues is "issues" in both), shall report a configured drive with no state database as not synced yet rather than up to date, and likewise a state database that has not completed a sync (no delta cursor and an empty baseline, as right after `drive reset-sync-state`), which a running watch shows as syncing, and render states as words in text output. `status` shall warn when a drive's state database cannot be read instead of showing it as empty. Text `status` shall name every drive's state, "Up to date" included, say when a watch is running for it, and count only files in its "Files" line. It shall list the paths behind its "Retrying" count with each item's action and attempt count. [verified]
- R-6.6.26: OneDrive and local file failures a user can understand shall print as one plain sentence naming the path the command was working on and the next step: not found (with the `ls` to run), access denied, already exists (for `mv`/`cp`, `--force`), locked, throttled, storage full, temporary server problems, answers from OneDrive that disagree on which folder holds the path (with no claim that nothing changed, since a confirmation wait meets them after its change), a name OneDrive cannot carry in a path (naming the `:`), and a missing or unreadable local file, named as the user gave it. HTTP status codes, request IDs, item IDs and package prefixes appear only in the `--verbose` details. A shared item's selector gets no `ls` hint, as it has no parent folder to list. A failure names each local path once: a single file's error through the filesystem call that failed, and a folder transfer's failure line in its subject, whose cause is printed without the path. [verified]
- R-6.6.27: Command-line mistakes (unknown command or flag, wrong argument count, conflicting flags) shall print the problem and the `--help` command for it, and exit 2, before any config or login work runs. A run stopped by Ctrl-C or SIGTERM exits 130 without an error line. A timeout or internal cancellation is reported as an error. Under the systemd journal, every line of the final error carries the err priority (`<3>`). [verified]
- R-6.6.28: A command shall not report success for work it did not do. One-shot `sync` exits non-zero when a selected drive could not sync, and exits 1 when a drive it ran left a file unsynced as the run's last pass ended: an action of that pass failed, work is queued to retry or was left for the next sync (the follow-up work of the plan the run ends on included, less what a one-way mode holds back), or the store holds an observation issue of a type that leaves a file unsynced, read from the snapshot `status` reads with `status`'s own filter. Retry work is not read from the store: every retry row a live pass leaves belongs to an action of that pass's plan, already counted as failed, still open or left, so each file is counted once, a file an earlier pass failed and a later pass of the same run finished is not left, and the exit status and `status` agree on every run, a persistent state such as a read-only shared folder included. Not work left: work `--upload-only` or `--download-only` held back, deletes held for `--confirm-deletes`, conflict copies, a paused drive beside a drive that ran, and `--dry-run`. Item-level failures are printed per file and kept as durable conditions that `status` reports. Folder `get`/`put` name every item they could not transfer and fail in text and `--json` mode alike. A failed SharePoint search fails `drive search` instead of printing an empty result, and an ambiguous `drive add` lists the candidates on stderr and fails. `drive remove --purge` reports sync data it could not delete. With `--json`, stdout carries only JSON: `status` prints an empty document when nothing is selected, and `sync` streams JSON lines (`start`/`watching`, one `activity` per file action, `summary` per drive, `stopped`). [verified]
- R-6.6.29: Transfer progress (`get`, `put`, `cp`) shall be one redrawn line on stderr, shown only when stderr is a terminal and the run is neither `--quiet` nor `--json`, and cleared before any other output. Piped and scripted runs get only the final summary. [verified]
- R-6.6.30: A persistent, unchanged condition shall be reported once, when it starts or changes, not on every watch poll, safety scan, retry or in-flight item: a skipped local file warns when first found; an unreachable OneDrive or shared folder warns once per outage and reports recovery once at NOTICE, which the default console shows, so a console that showed the outage also shows its end; a block scope (throttling, full storage, missing permission) is reported once when it activates; a degraded wake source or folder-delta fallback is reported once at INFO; a blocked shared-folder cleanup is persisted and warned once, never returned as an error; a failing rescan after dropped watch events warns once per distinct failure; a removed shared folder whose local copy is kept is noted once at INFO. Repeats log at DEBUG, and the condition stays visible in `status`. A housekeeping step that keeps failing (refreshing the shared-folder list, removing leftover download files, removing expired upload session files, purging the sync trash) has no `status` entry: it warns once per failure streak, logs repeats at DEBUG and notes its recovery once at INFO. Self-healing conditions (throttling being handled, service outages, websocket fallback, delta expiry, dropped watch events, eventual-consistency probes) shall not be WARN. A grouped warning for many skipped files shall state the group's reason, using one file's detail only when every file in the group shares it, and name example paths in the sentence rather than as a raw attribute. [verified]
- R-6.6.31: The exit status shall tell a service manager whether running again unchanged can succeed. 0 is success, 2 a command-line mistake, 130 a run the user stopped; 77 (EX_NOPERM) means sign-in is required (no saved login, or Microsoft rejected or revoked it), 78 (EX_CONFIG) means the configuration is invalid (unreadable or unparsable file, failed validation, a drive selector that matches nothing, no drives configured), and 65 (EX_DATAERR) means a drive's saved sync state needs the user (a newer version wrote it, it is damaged, or nothing says which version wrote it; R-2.5.9). Every other failure, including network, throttling and server errors, exits 1, and so does a one-shot `sync` that finished but left a file unsynced (R-6.6.28): running it again may finish the work, and a drive error that exits 77, 78 or 65 is reported first. `sync --watch` exits 77, 78 or 65 only when every drive that could not start failed for that same reason. `sync --watch` with every selected drive paused is not a failure: it starts, says so, and idles until a drive is resumed or it is stopped (R-3.4.2), so a restarting unit does not loop. The status is chosen from typed errors, never from message text, so a unit can set `RestartPreventExitStatus=65 77 78`. [verified]
- R-6.6.32: When `$NOTIFY_SOCKET` is set, `sync --watch` shall speak the systemd notify protocol for a `Type=notify` unit: `READY=1` once every drive that could start is running its watchers, a one-line `STATUS=` ("Watching ~/OneDrive", "sign-in required for Work", "Sign-in required: run 'onedrive-go login'" on exit), `RELOADING=1` with `MONOTONIC_USEC=` and then `READY=1` around every config reload whether or not it applied, `STOPPING=1` when shutdown starts, and `WATCHDOG=1` at half of `$WATCHDOG_USEC` when the watchdog is for this process. Path and abstract (`@`) sockets are supported without libsystemd; an unusable socket is a warning and sync continues. Outside systemd nothing is sent. [verified]
- R-6.6.33: `--json` is a global flag, so every command shall either honor it or refuse it; none may ignore it. A command that honors it prints exactly one JSON document on stdout (`sync` streams JSON lines), drops its prose confirmation, keeps warnings, prompts and errors on stderr, and exits as it would without `--json`; a command whose run partly failed still prints the document and exits non-zero. Every document and every `sync --json` line prints `&`, `<` and `>` as themselves, never as Unicode escapes, and a list with nothing in it prints `[]` (or, for a list the document leaves out when empty, nothing), never `null`. When output cannot be printed, the error on stderr names the step that failed: `write JSON output: ...` when stdout would not take the bytes (a closed pipe), `encode JSON output: ...` when the value could not be encoded. The `summary` line of `sync --json` gives a drive that left work (R-6.6.28) the status `incomplete`, with `failed`, `will_retry` (work queued to retry or left for the next sync) and `still_open` (the files a condition `status` lists keeps unsynced: its observation issues, and the last pass's failures such a condition refused, whose `activity` lines have the status `still_open` and name the condition, R-2.10.71; a file the last pass only held until its retry is due is in `will_retry`): the numbers of the text summary and the exit status, which describe the run's last pass, each file once. This covers the mutating commands too: `login`, `logout`, `pause`, `resume`, `drive add`, `drive remove`, `drive reset-sync-state` and `recycle-bin empty` print their result as JSON. A form with no result to print (`drive add` without a drive) refuses `--json` as a usage error (exit 2) before doing anything. [verified]
- R-6.6.35: A `sync --watch` that stops with an error, including one that refuses to start (its sync folder missing, another sync owning the control socket), shall write the reason to the log file as well as the terminal, so the log holds the whole history of a watch that a service manager keeps restarting. The terminal shows the reason once. [verified]
- R-6.6.36: Under a unit that sets `WatchdogSec=`, `sync --watch` shall send `WATCHDOG=1` only while its watch loop shows progress: the loop beats at the top of every iteration and on an idle tick, and declares each step that can hold it longer (starting, a drive's start or stop, a config reload, a drive's event, a pass over the drive set) with that step's limit; a loop silent past its limit (60 s outside a declared step, the step's limit inside one) gets no keepalive and one Error line naming the step, so systemd restarts the process. A false alarm costs a restart, not data. [verified]
- R-6.6.37: A `sync` whose stdout refuses a line of its report (a full disk or an I/O error on a redirected stdout; a closed pipe ends the process with SIGPIPE before any code sees it) shall finish its work, one-shot or `--watch`, text or `--json`, and say so once on stderr ("Warning: sync output is incomplete: ..."), however many lines fail after it; when the run ends with no other error, that write is its error and it exits 1, so a script reading the output cannot take a cut-off report for a whole one, and when the run also failed or left work, the run's error is the one returned. A stderr line of the sync console (a failed or retried file action, a drive's error, held deletes) that cannot be written is recorded like any refused status line (R-6.6.31), so a sync that otherwise worked exits 1. [verified]
- R-6.6.38: Durations and sizes a person reads shall be worded by one formatter in human units: a wait, a delay or a limit in whole seconds and never below "1 s", a measured time in tenths of a second below a minute, both rounded before they are split, minutes and seconds from a minute up with a zero part dropped, and hours and whole minutes from an hour up; sizes with one decimal in the largest unit reached. `--json` keeps its numbers. [verified]
- R-6.6.34: Azure AD outcomes a user can act on shall be one plain sentence, not raw OAuth/AADSTS text: `interaction_required`, AADSTS50076 and AADSTS50079 say Microsoft requires a new interactive sign-in (multi-factor authentication or a sign-in policy) and, when met at token refresh, also count as sign-in required; AADSTS65001 and AADSTS65005 say the account or organization has not allowed the app; "not enabled for consumers" says the app registration accepts only work or school accounts. [verified]

## R-6.7 Technical Requirements [verified]

Constraints derived from the OneDrive API that the system must satisfy for correctness. See [graph-api-quirks.md](../reference/graph-api-quirks.md) for the underlying API behaviors.

- R-6.7.1: The system shall handle delta operation reordering (deletions arriving after creations at the same path). [verified]
- R-6.7.2: The system shall normalize driveId values across all endpoints to a canonical form. [verified]
- R-6.7.3: The system shall track items by ID and reconstruct paths from parent chains. When both the parent-ID chain and `parentReference.path` can place an item, the ID chain wins. The executor's live preflight likewise checks a live item's location by parent ID plus NFC name, not by a path rebuilt from `parentReference.path`. [verified]
- R-6.7.4: The system shall detect server-side file modification after upload (SharePoint enrichment) and not re-upload. [verified]
- R-6.7.5: The system shall handle HTTP 410 (delta token expiry) with full re-enumeration, including orphan detection (R-2.15.3). [verified]
- R-6.7.6: The system shall enforce upload chunk alignment to 320 KiB boundaries. [verified]
- R-6.7.7: The system shall not compare hashes for deleted items. [verified]
- R-6.7.8: The system shall treat item names in API responses as opaque and pass them through verbatim, never URL-decoding them, and shall put a name or an item ID into a route escaped as one path segment. [verified]
- R-6.7.9: Sync remote observation shall filter out OneNote package items (`type: "oneNote"`) that lack standard file/folder facets; direct Graph-backed file operations shall still expose provider-visible package items. [verified]
- R-6.7.10: The system shall deduplicate identical items appearing multiple times within a single delta response, keeping the last occurrence per item ID. [verified]
- R-6.7.11: The system shall filter out phantom system drives provisioned by Microsoft for Personal accounts (face crops, albums) that return HTTP 400 on access. For Personal accounts, the system shall use `GET /me/drive` (singular) to discover the primary drive. [verified]
- R-6.7.12: When `GET /drives/{driveID}/items/root/children` returns transient HTTP 404 with Graph code `itemNotFound` for a valid resource (cross-datacenter load balancer timeout), the system shall classify it as transient and retry with backoff. [verified]
- R-6.7.13: When `GET /me/drives` returns HTTP 403 with Graph code `accessDenied` shortly after token refresh (eventual consistency), the system shall classify it as transient and retry with backoff. The current production retry budget is 5 total attempts with the standard 1s base, 2x multiplier, ±25% jitter, and 60s cap. [verified]
- R-6.7.14: When a path-oriented delete resolves a target path successfully and the immediate `DELETE /drives/{driveID}/items/{itemID}` still returns HTTP 404 with Graph code `itemNotFound`, the system shall treat that as a transient path/delete convergence quirk. CLI path deletes shall re-resolve the path, retry the delete against the current item when needed, and accept a now-missing path as success. [verified]
- R-6.7.15: The system shall truncate local timestamps to zero fractional seconds before comparing them with OneDrive's whole-second values. Comparisons of one local observation with another (the hash fast path, preconditions) use full precision (R-2.2.4). [verified]
- R-6.7.16: The system shall safely handle missing or invalid timestamps (`0001-01-01T00:00:00Z`, absent `lastModifiedDateTime` on deletions) without panicking, preserving them as unknown rather than fabricating replacement values. [verified]
- R-6.7.17: When a file completely lacks hashes (zero-byte files, certain Business/SharePoint files), the system shall use a fallback comparison of size + mtime + eTag. [verified]
- R-6.7.18: When extracting identity data for shared items, the system shall use a four-level fallback chain: `remoteItem.shared.sharedBy` → `.owner` → `remoteItem.createdBy` → top-level `shared.owner`. [verified]
- R-6.7.19: The system shall not advance the delta token when a delta response contains zero events, to prevent permanently missing ephemeral deletion events. [verified]
- R-6.7.20: The system shall adapt observation methods based on mount-root capability: Personal shared-folder mount roots may use folder delta when Graph supports it, while Business/SharePoint shared-folder mount roots use standard enumeration. [verified]
- R-6.7.21: The system shall handle shared folder items whose parent IDs reference a different drive (the sharer's drive), including driveId truncation and casing normalization on cross-drive references. The planner detects and decomposes cross-drive moves into separate delete + upload actions since MoveItem is a single-drive API. [verified]
- R-6.7.22: When the API's path-based query returns an item from an incorrect path (fuzzy matching bug), the system shall post-validate the returned item against the requested path: by its parent path and name when Graph returns the parent path, otherwise by its name and by its parent's ID against the folder read at the parent's path, at a cost that does not grow with the path's depth. An item the answers put elsewhere is not found; answers that do not agree on the folder at the path shall be an error that no caller takes for an absent item, and that a wait for the path to become visible reads again on. A listing by path shall hand on only the children its answers place at the path, by the same rules. The validation reaches as far as the answers tell: answers without a parent path that agree on a folder of the right names in another subtree two or more levels up are not detected. A name a path route cannot carry (one holding `:`) shall be refused before any request. [verified]
- R-6.7.23: The system shall keep `parentReference.path` verbatim after its `/drives/{id}/root:` prefix, never URL-decoding it (live probe L-32: Graph does not encode it), preserving a separate known-path flag so root parent paths are distinguishable from omitted/invalid paths. [verified]
- R-6.7.24: When a folder is renamed, the system shall infer and recalculate path changes for all descendants, since only the renamed folder appears in the delta response. [verified]
- R-6.7.25: When re-uploading a modified file to Business/SharePoint, the system shall accept the unavoidable extra version created by the API (unfixed Microsoft bug) without attempting futile workarounds. [verified]
- R-6.7.26: The system shall handle absent `lastModifiedDateTime` (null) on API-initiated deletions without error, preserving the timestamp as unknown. [verified]
- R-6.7.27: When classifying errors, the engine shall handle empty `DriveID` (local-only operations like `os.ErrPermission`) by skipping remote scope routing. Only remote API errors shall require drive-aware scope routing. [verified]
- R-6.7.28: The system shall skip malformed remote delta items that lack the identity or materialization data required to produce a safe stored row and change. Non-root items with empty `id`, non-deleted items with empty `name`, and delete entries whose path cannot be recovered from the baseline or from a surviving delta name plus parent/path context shall be warned and skipped instead of emitting empty-ID, empty-path, or parent-path delete events. Unknown-parent non-delete entries shall make the remote observation batch incomplete so the cursor does not advance past provider truth that could not be materialized safely. [verified]
- R-6.7.29: The system shall treat sparse non-delete delta items as partial updates. When Graph omits unchanged `name` or `parentReference`, remote observation shall recover the missing path fields from exact Graph parent paths or the baseline instead of re-rooting the item. [verified]
- R-6.7.30: The system shall bound every API response body it buffers in memory, so a malformed or hostile response cannot dictate client memory use. A success body larger than its bound shall be reported as an error rather than silently truncated. An error body is read up to its bound (64 KiB) and the rest is left unread: the error is built from the bytes read, and the debug record of the failed answer gives their count, which is the bound when the body was cut there. [verified]
- R-6.7.31: The system shall not panic on externally supplied values, including user-editable configuration and catalog entries, API responses, and filesystem state. A value that cannot be parsed shall be reported as an error or degraded to a documented empty value, never treated as a programmer error. [verified]
- R-6.7.32: Every paged Graph listing shall follow `@odata.nextLink` to completion, and every page loop shall be bounded so a circular or buggy continuation fails with an error instead of looping indefinitely. [verified]
- R-6.7.33: A 2xx mutation answer whose body is empty (204), not a driveItem, or an item without `id` shall be resolved by reading the item back by ID, never reported as a failure of the mutation that succeeded nor returned as an item without identity. An upload completion without an item is reported as `ErrUploadCompletedWithoutItem` so the transfer layer looks it up. [verified]
- R-6.7.34: An item's modification time shall come from `fileSystemInfo.lastModifiedDateTime` when Graph reports it (the top-level `lastModifiedDateTime` is the server's, which renames and moves bump), falling back to the top level. A modification time the client sends shall never be the zero time and shall be clamped to 1900-01-01T00:00:00Z or later (live probe L-26), warning once. A download's recorded local mtime shall be what the filesystem holds afterwards, not the time that was requested. [verified]
- R-6.7.35: When Graph answers HTTP 403 `accessDenied` whose inner code is `serviceReadOnly` (a Microsoft-side read-only window), the system shall not retry it as the token-propagation lag of R-6.7.13, and shall report it as a provider read-only window, distinct from a permission refusal; an `accessDenied` without that inner code keeps its own meaning. [verified]
- R-6.7.36: A drive ID or a SharePoint site ID shall go into every request route by one rule: as it is (a Business drive ID's `!` and a site ID's commas unescaped), and an ID that is empty or holds `/`, `?`, `#` or `%` shall be refused before any request is sent. [verified]
- R-6.7.37: A lookup of one name in a folder (a create refused with 409 in `put`, `mkdir` and sync, a create answered without its item, a folder create answered with an empty body, a name below a mounted folder) shall read the one name first and list the folder only when that read cannot settle it (not found, not addressable by the path route, or 400), a page at a time, stopping at the page that holds the name as spelled, with every outcome the whole listing gave. [verified]
- R-6.7.38: A remote path shall be resolved by one rule in every command that resolves one (`stat`, `get`, `ls`, `rm`, `put`, `mkdir`, `mv`, `cp`) and in the visibility wait after a mutation: a name the path route is known not to resolve (one holding `:`, one starting with `v1.0`, the name `$value`) shall never be path-addressed, but found in its parent's listing, with the walk going on by ID; a path read answered 400 shall be resolved the same way from the drive root; a genuine miss shall cost one request and report not found. [verified]

## R-6.8 Network Resilience [verified]

- R-6.8.1: The system shall respect 429 (Too Many Requests) with Retry-After headers. [verified]
- R-6.8.2: The system shall use exponential backoff with jitter for transient failures. [verified]
- R-6.8.3: All transfers shall be resumable after network interruption. [verified]
- R-6.8.4: The system shall treat HTTP 429 as target-scoped by default: it shall block only the narrowest remote boundary provable from the failed request. Owned-drive traffic blocks that drive, and shared-folder mount-root or direct shared-item traffic block that exact remote root/item boundary. Broader account-wide or tenant-wide throttling shall not be inferred without explicit evidence. [verified]
- R-6.8.5: ~~The system shall parse `RateLimit-Remaining` headers and proactively slow when less than 20% remains.~~ [cancelled — SharePoint Online documents that it does not return or support IETF RateLimit headers and that clients should honor Retry-After instead; reactive 429 scope handling with exact Retry-After is sufficient. See graph-api-quirks.md "Throttling Scopes".]
- R-6.8.6: The system shall honor `Retry-After` from both 429 and 503 responses, populating `GraphError.RetryAfter`, in either form RFC 9110 allows: delay-seconds, or an HTTP-date measured against the response's `Date` (this host's clock only when `Date` is missing or unparsable). A value too long to represent shall saturate rather than wrap to a short or negative wait; no cap is applied (R-2.10.7, R-2.10.14). An unusable value is treated as no `Retry-After`. [verified]
- R-6.8.7: During sync, workers shall never block on retry backoff. Failed actions are completed once and recorded durably in `retry_work` or `block_scopes`; workers block only for HTTP round-trip time. [designed]
- R-6.8.8: For sync operations, the graph client shall use the tuned transport without the retry transport (`graphtransport.SyncClientSet`). Each dispatch equals one HTTP request. CLI commands shall retain `Transport` policy (`MaxAttempts: 6`, the first attempt included). The retrying transport shall not start a wait (a `Retry-After`, a backoff, a throttle deadline an earlier 429 set) that would end after the request's deadline: it returns the answer it has at once instead (the 429 or server error, the network error, or, for a throttle wait, the request unsent as throttled), so the caller classifies what OneDrive said rather than the deadline. A request without a deadline waits as before. [verified]
- R-6.8.9: The executor shall not contain a retry loop. It shall dispatch actions and return results; the engine shall classify and schedule retries. [verified]
- R-6.8.10: Each retryable sync action failure shall be recorded in `retry_work` with `next_retry_at` computed by the `retry.Reconcile` backoff policy. Due rows are revalidated from current truth and reintroduced through the normal planner/dependency pipeline. One durable retry mechanism, one backoff curve. [designed]
- R-6.8.11: The system shall use `retry.Reconcile` backoff for all durable retry work: 1s base, 2× multiplier, ±25% jitter, 1h max. Curve: 1s, 2s, 4s, 8s, 16s, 32s, 64s, 128s, 256s, 512s, 1024s, 2048s, 3600s cap. The persistent mechanism is `retry_work` plus engine-owned retry/trial loops. [designed]
- R-6.8.12: Target drive identity shall flow through the pipeline without lookup: planner to Action to TrackedAction to WorkerResult to engine. No component shall query drive identity from DB or API during failure handling. [verified]
- R-6.8.13: `Action` shall expose `TargetsOwnDrive() bool` and `ShortcutKey() string` as the only drive-identity accessors for scope matching and routing. [verified]
- R-6.8.14: Sync callers use the tuned transport without the retry transport. The graph client's `doOnce()` still performs transparent 401 token refresh: when the token source hands back the rejected token unchanged, the refresh is forced (one token-endpoint call per 30 s, shared by concurrent 401s) and the request retried once. The retried request shall carry exactly the bytes of the original body: the authenticated request helpers take the body as bytes and build every attempt from them, so a body that cannot be replayed cannot be passed. Auth refresh is lifecycle, not transient retry. When refresh fails, or a 401 follows a successful refresh without naming a server-side fault, the system shall return `ErrUnauthorized` (fatal). A 401 that a freshly refreshed token still gets with "Unable to initialize RPS", `generalException`, or an `invalid_token` challenge that does not say "expired" shall be `ErrAuthTransient` instead. [verified]
- R-6.8.15: The engine shall classify the following HTTP status codes as transient: 5xx (`server_error`), 408 (`request_timeout`), 412 (`transient_conflict`), 404 (`transient_not_found`), 423 (`resource_locked`). Transient exact work is recorded in `retry_work` with `next_retry_at` (backoff via `retry.Reconcile`: 1s-1h). Shared transient conditions activate `block_scopes`. In one-shot mode, failed work remains durable for the next `onedrive-go sync` invocation to replan, and the run that leaves it exits 1 (R-6.6.28). [designed]
- R-6.8.16: External and runtime failures shall be translated into the documented domain error model before retry, durable persistence, or user presentation. [verified]
- R-6.8.17: Errors from pre-authenticated requests (downloads, upload sessions, copy monitors, Socket.IO notification endpoints) shall never carry the pre-authenticated URL, whose path or query embeds a credential, whether the error is returned, logged or copied into a lifecycle event. Transport failures keep their cause and the URL host, so users can still tell which service failed. [verified]
- R-6.8.18: Every request to Graph, upload and download hosts shall carry one User-Agent in Microsoft's decorated form, `ISV|onedrive-go|onedrive-go/<version>`, built in one place (`graph.UserAgent`) for every command and the sync engine. [verified]
- R-6.8.19: A request the transport retries shall resend its complete body with an exact `Content-Length`. A request whose body cannot be replayed shall be returned to the caller after one attempt, never resent with the bytes the first attempt consumed. [verified]
- R-6.8.20: A transfer body (download response or upload fragment) that moves no bytes for 2 minutes shall be abandoned with a retryable stalled-transfer error, keeping a download's partial for resume; a stall whose silence was on the local side (an upload's read of the local file, or a download's write of it between two body reads) shall say so, and the transfer shall return at once and free its worker while the stuck call is still blocked, leaving the call to a bounded process-wide record of abandoned local calls (a transfer waits for its call when the record is full), with no abandoned read or write able to land in the next attempt's buffer or partial file; sync shall retry that file as busy (as `local_call_abandoned` when the call was left behind, R-6.8.32) and never count it as evidence of a service outage; any other response body that brings no byte for the same 2 minutes while it is read shall fail with a retryable stalled-response error (an error answer whose body stalls is reported as that answer), and one that keeps moving, however slowly, shall not; an answer the Graph client does not read, one it retries or a redirect it follows, shall be closed unread. Transfer and metadata connections shall ping idle HTTP/2 connections and close one whose ping goes unanswered, and a request or a body read on a connection so closed shall fail with a lost-connection error of its own type. [verified]
- R-6.8.21: A retrying (CLI) transport shall resend a file or folder create after a transient failure, because the create uses `conflictBehavior=fail`: a replay of a create that committed answers 409 and creates nothing, and every caller takes a 409 on create as "look at what holds the name". Other `POST` and `PATCH` requests shall stay unretried at the transport. [verified]
- R-6.8.22: Every server-supplied pre-authenticated URL (`@microsoft.graph.downloadUrl`, upload session, copy monitor, `/content` redirect target, Socket.IO notification endpoint) shall be followed only when it is HTTPS on an allow-listed Microsoft host and not an IP literal. A refused URL shall fail before any request is sent, and the refusal shall not echo the URL. [verified]
- R-6.8.23: Files onedrive-go creates that name accounts or items — the config file and log files — shall be readable by their owner only (`0600`), and every folder it creates for its own state (config, data, logs, locks, upload sessions, trash) shall be `0700`, as the XDG base directory rule asks of a directory created where none existed. A folder that already exists keeps its mode; the sync folder is the user's and is not covered. [verified]
- R-6.8.24: After a throttle (or any timed block scope) a successful trial shall re-admit the blocked work in a ramp, not all at once: a first batch bounded by the transfer worker count (at least 4), doubling after each batch that completes without a further 429 up to half the batch that last drew a 429 (the slow-start threshold, persisted with the scope so one-shot passes and restarts keep it), growing by one per batch from there. A 429 inside the ramp shall re-block the scope with the new `Retry-After`, record the threshold, and restart the ramp from the first batch; a scope's trial shall never move earlier than a deadline it already holds, since the transfers in flight when a throttle hits answer with successively later `Retry-After`s that reach the engine in any order. Admitted work that a scope activation blocks and that no worker has started yet shall be taken back and held under the scope rather than dispatched, and nothing shall be sent to the blocked target before the scope's trial is due, including by a run started inside the `Retry-After`, so the 429s one episode costs are bounded by the transfers in flight when it hits. The scope is removed, and "Resumed syncing" said, once, when its last blocked row is released. A released batch's members shall be admitted spread over a short window (up to 1 s, uniformly per member, on the engine clock), not in the instant of the release; the server-given `Retry-After` is honored as given, without jitter. [verified]
- R-6.8.25: A fresh plan with no active throttle scope for a drive (a one-shot start, the watch bootstrap, each replan) shall open into its backlog in slow start, not at full `transfer_workers` concurrency: at most 2 of that drive's actions in flight at first, doubling after each round of that many successful completions up to the worker pool size, per drive, without starving dependency-ordered work (an action whose dependents wait counts as one in flight, nothing more). A 429 during the slow start hands the drive to the throttle scope of R-6.8.24, which owns re-admission from there; a drive already under a throttle scope when the plan starts is the scope's from the start; the allowance is per plan and starts over with the next. [verified]
- R-6.8.26: A refreshed sign-in that cannot be saved to its file shall be an error, never only a warning, and shall never fail the requests that use it: a one-shot command shall do its work and then exit non-zero with a message that names the file and the cause; a watch shall report it once per distinct failure, name the file in its service status while the failure lasts, keep syncing, keep retrying the save, and exit non-zero when it is stopped while the save is still failing. - R-6.8.27: Within one process — whose one session runtime owns the command's Graph clients and, for `sync`, its engines' — one sign-in file shall have one token source: identity probes, drive and shared-item discovery, SharePoint search, shared-drive naming and drive sessions all take it from the runtime, so a refresh one of them makes is the token every other one uses. Only a refresh that finished with a token writes the saved sign-in. [verified]
- R-6.8.28: A command that asks OneDrive only to add live details to what it knows locally shall not wait on OneDrive without a bound. `status` asks every account at the same time, under one budget of 10 s for all of them, for its profile (display name, sign-in proof) and its configured drives' storage. The budget covers the whole of each request, its token refresh (R-6.8.27) and its retry waits (R-6.8.8) included. An account whose answers do not arrive within the budget, whose profile request fails for a reason other than sign-in, or whose storage request OneDrive throttles or fails with a server error, shows its local state, and `status` says so on stderr, one line per account with the reason in plain words (what OneDrive answered, such as "OneDrive had a temporary server problem", or "OneDrive did not answer within 10 s"), so `--json` keeps stdout one document; it exits 0. [verified]
- R-6.8.29: An action's failure is a shutdown only when the run's own context has ended and the failure is that end's cancellation, never because of the shape of its error alone; an observer loop stops on any failure once its run has ended. A request that timed out (a response-header, dial, TLS handshake or whole-request transport timeout, an expired request deadline, a stalled transfer, an answer whose body stalled, a read whose connection the keepalive closed, or a request whose HTTP/2 connection was closed for an unanswered ping before or while its answer was read) while its sync run goes on shall be a failure like any other network failure: the action is kept as retry work and shown, a page of the change list is retried under its policy, and a watch poll backs off and polls again. [verified]
- R-6.8.30: Two processes that share one sign-in shall never invalidate each other's: a refresh shall read the sign-in file under a lock shared by every process, use a newer sign-in another process wrote instead of redeeming its own, and wait for another process's refresh no longer than a bound that outlasts one sign-in request; a sign-out shall not be undone by a running watch, whose refresh finds the file gone, writes nothing and reports sign-in required. [verified]
- R-6.8.31: A file command shall need only its drive's endpoints. The check of who the account is (the email OneDrive reports for it, which only relabels local names) shall never fail or stall a command: a failure other than a rejected sign-in is logged and the command goes on with the stored identity, each check has a budget of 5 s covering its retry waits, commands that check several accounts check them at the same time, and a check is asked only when due: 24 hours after one OneDrive answered (or a sign-in), 15 minutes after one it did not. [verified]
- R-6.8.32: A file whose transfer returned while its read (an upload) or write (a download) of the local file was still stuck, left to the record of abandoned local calls (R-6.8.20), shall be recorded in the state store under the condition `local_call_abandoned` from the first such failure, so that `status`, run as another process, lists the file under "Local file stopped responding" instead of as anonymous retrying work; the file shall be retried on the durable curve (from 30 seconds, doubling), never every second against a disk that does not answer, and never count as evidence of a service outage; a stall the transfer waited out because the record was full stays `local_busy`; the record shall be cleared when the file next syncs, and replaced when a later attempt fails another way. [verified]
